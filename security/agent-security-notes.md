# Agent Security Notes

Security design record for the Expense Tracker Dashboard: the human threat
model, the agent-specific threat model, the design-choice log, the accepted
limitations, and the Accepted Findings register that binds every measured
scan finding to a disposition (REQ-SEC-095, REQ-SEC-090/091/094,
REQ-SEC-074). All statements below describe the shipped tree only — the
vocabulary is cross-grepped against the code and the agent extension pack.

## Security Layers

Defense is layered and each layer re-enforces the one above it (the
in-depth table the extension-pack documentation also cites):

| Layer | Mechanism | Enforces |
| --- | --- | --- |
| Client hooks | `agent-hooks/validate-amount.py`, `validate-ownership.py` | Bad input never leaves the agent |
| API schema | Pydantic schemas, frozen payload key sets | Shape violations reject with 422 |
| Service | Ownership filters, same-transaction audit | Cross-user access and silent writes |
| Database | FKs, CHECK constraints, unique pins | Last line before persisted state |
| Platform | Render secret store, `.gitignore` hygiene (REQ-SEC-120/121) | Secrets never reach the tree |

A bypassed hook still fails at the API, and a bypassed API check still
fails at the database; the layers are redundant by design.

## Assets

| Asset | Sensitivity | Why |
| --- | --- | --- |
| User expense rows | High | Personal spending history, locally owned (REQ-AI-133 local-only data) |
| Budget rows | Medium | Spending limits reveal income patterns |
| `audit_logs` table | High | Proves who changed what and when |
| `JWT_SECRET` | Critical | Forges any session if leaked |
| Password hashes (bcrypt) | High | Offline cracking target if exfiltrated |

## Threat Actors

- Outsider on the network probing the public surface for unauthenticated
  reads or auth bypass.
- Authenticated user attempting horizontal access to another user's
  expenses or budgets.
- Malicious or compromised AI agent / subagent acting on published or
  injected content (see Agent Threat Model).
- Insider with repository access attempting to leak or silently alter
  data or audit history.

## Threats and Mitigations

| Threat | Mitigation |
| --- | --- |
| Credential stuffing / password guessing | bcrypt cost 12 passlib context; login errors never distinguish unknown user vs wrong password |
| Session forgery | HS256 JWT with `iss`/`exp` validated; algorithm set comes from settings, never from the token |
| Horizontal privilege escalation | Every query filters `user_id == current_user.id`; ownership hook re-enforces client-side |
| Silent data mutation | `write_audit_log` joins the caller's transaction — an audit failure rolls the business write back (REQ-PROD-021) |
| Secret exfiltration through the repo | gitleaks gate measures zero findings; platform secrets are Render-sourced (REQ-SEC-120) |

## Out of Scope Threats

- Multi-tenant hard multi-tenancy attacks: the deployment is a single
  local/free-tier instance with row-level ownership scoping, not a shared
  hostile-tenant platform.
- Supply-chain compromise of the base images themselves: addressed by
  pinned lockfiles and scan registration, not by image signing in this
  phase.
- Physical access to the machine hosting the local instance: assumed
  trusted per the local-only data statement (REQ-AI-133).

## Audit Log Example

The documented trail is the code's, not an invented one — measured from
`backend/app/audit/logger.py` and the `audit_logs` model:

```json
{
  "table": "audit_logs",
  "user_id": "7c1f...",
  "action": "CREATE",
  "entity_type": "expense",
  "entity_id": "9a3b...",
  "old_value": null,
  "new_value": {"amount": 12.5, "date": "2026-10-12", "category_id": "3e77...", "note": "coffee"},
  "ip_address": "127.0.0.1"
}
```

Value-shape directions measured from the writer docstring: CREATE leaves
`old_value` NULL; UPDATE carries both values; DELETE carries `old_value`
full and `new_value` NULL. `entity_type` is `expense` or `budget`
(`ck_audit_entity_type`), `action` is CREATE / UPDATE / DELETE
(`ck_audit_action`), and payload keys are frozen — categories are
deliberately not audited (REQ-SEC-062).

## Non-Functional Security

Password hashing is bcrypt (passlib CryptContext, rounds=12, automatic
salts, REQ-SEC-020). Token issuance is HS256 JWT.
The rate-limiting posture is measured: no rate limiting ships in this
release, and that absence is registered as an accepted limitation and a
P1 future improvement rather than claimed as a control.
HTTPS termination, secret management, and cold-start behavior follow the
Render platform contract (`render.yaml`, `ops/runbook.md`).

## Agent Threat Model

The agent surface is the extension pack: three skills, two hooks, four MCP
tools, two read-only subagents (docs/agent-extension-pack.md).
Every agent read or write goes through the public HTTP API with a real JWT
— the MCP server is not the database and never touches it.
The threat model therefore reduces to: an agent acting for a user holds
that user's privileges and nothing more (no superuser role exists in the
model), and any capability escalation must be attempted through the same
API a hostile user would face.
The subagents are read-only by definition; the budget-check and
monthly-report skills report and warn, they never change data.

## Agent Security Controls

- `validate-ownership.py` raises `PermissionError` before any call that
  would touch another user's resource; the same rule is re-enforced in the
  backend schema, service, and database layers.
- `validate-amount.py` rejects invalid amounts before an expense is
  created; hooks raise, the agent must surface the error, never swallow it.
- The MCP tools are four thin wrappers over the public HTTP API; no tool
  holds database credentials, so a compromised agent process leaks at most
  one user's JWT.
- `docs/permissions.md` is the access matrix: skills, hooks, and subagents
  each map to allowed API families, and violations escalate as surfaced
  errors, not silent retries.

## Prompt Injection

The injection surface is untrusted content the agent is asked to process:
expense notes, category names, and repository text.
An injected instruction inside a note cannot create privileges — the
agent's authority is its user's JWT, and the ownership hook plus the API
ownership filter bound what that JWT can reach regardless of what the
model is told.
The residual risk is behavioral (an agent tricked into writing
attacker-chosen expense rows within its own user's scope), which the audit
trail makes attributable and reversible.
Skills are procedures in SKILL.md files, not code paths; changing agent
behavior requires a repository change that the PR audit and
gitleaks/semgrep scans cover.

## Design Choices

- Auth and tokens: HS256 JWT issued by the auth routes; the algorithm list
  always comes from settings, never from the token header (no algorithm
  confusion accept-path in our own code). Passwords are bcrypt cost 12 via
  a single passlib CryptContext.
- Audit: same-transaction audit writing (no separate session, no separate
  commit) so business write and audit row commit or roll back together;
  schema changes ship only through alembic migrations with a single head
  (005), so migration history and audit schema cannot drift.
- Secrets and scans: platform secrets are Render-sourced
  (`fromDatabase`/`generateValue` in render.yaml), never literal; the five
  scan commands (gitleaks, semgrep, trivy, pip-audit, npm audit) are the
  Makefile `security` target and their committed reports are the frozen
  measured input of the register below.
- Agent security: agents speak only the public HTTP API with a real JWT;
  read-only subagents; hooks as pre-flight guardrails with server-side
  re-enforcement, so no agent-only trust boundary exists.

## Accepted Limitations

Thirteen rows — one row added by the t87 accepted-findings refresh (the
tracing measurement gap below) on top of the twelve-row REQ-SEC-095/REQ-SEC-110
baseline. Each carries the why-accepted rationale and the future improvement
cell.

| # | Limitation | Why accepted | Future improvement |
| --- | --- | --- | --- |
| 1 | No rate limiting on auth or API routes | Accepted since the release is a local/free-tier single-user-per-account dashboard and adding limiter middleware would change the frozen error-envelope contract mid-phase | Add a token-bucket limiter on /auth routes as the P1 improvement below |
| 2 | No security headers / CSP / HSTS configuration | Accepted since the frontend ships on the Render free tier without a custom edge and the app stores no cookies (JWT bearer), so header-based attacks are mitigated by the absence of the attack surface | Ship a header middleware or edge config with a locked-down CSP |
| 3 | No MFA on login | Accepted because bcrypt plus short token expiry bound the blast radius of a stolen password for the local-only use case | TOTP second factor behind a recovery-code flow |
| 4 | No key rotation for JWT_SECRET | Accepted since the secret is Render-sourced and manual rotation is affordable at this scale; sessions are short-lived | Introduce kid-tagged keys with overlap window |
| 5 | python-jose CVE-2026-85394 has no published fix version | Accepted because our decode path pins the algorithm from settings and never accepts the header's algorithm, so the confusion precondition is not reachable in shipped code | Replace python-jose with a maintained verifier at the next dependency window |
| 6 | Dependency advisories are registered, not remediated | Accepted because `npm audit fix --force` and blind bumps cross the frozen dependency ranges and would break the green 187-test frontend; remediation is a dedicated backlog task | Scheduled dependency-window bumps with re-measure |
| 7 | Audit rows are not hash-chained | Accepted because same-transaction writing plus DB-level integrity already prove authorship for the shipped threat model | Add HMAC chaining over (prev_hash, row) |
| 8 | SQLite fallback stores data unencrypted at rest | Accepted since the fallback exists for local development only and production uses managed PostgreSQL | Document and wire an encrypted-at-rest option |
| 9 | `ip_address` is best-effort behind proxies | Accepted because the local/free-tier deployment has no proxy chain today; the column records what it can honestly observe | Forward real client IP via trusted proxy config |
| 10 | Agents reuse the owner's full-scope JWT | Accepted because scoped tokens would fork the API contract mid-phase while ownership filters already bound reach | Issue short-lived low-scope tokens for agent sessions |
| 11 | Dockerfile carries no HEALTHCHECK (trivy DS-0026) | Accepted because /api/v1/health exists and ops/health-check.md documents the probe; the image check is a style finding, registered below | Add a HEALTHCHECK instruction in the image task |
| 12 | docker-compose secrets are placeholder-only with manual rotation | Accepted because compose is the local path and real secrets live only in the Render secret store (REQ-SEC-120/123 markers verified by the composite gate) | Wire a secrets manager for non-Render deployments |
| 13 | Distributed tracing is NOT implemented for this milestone: spans are never measured, so the traces leg of the security/observability loop cannot be scanned or dispositioned | Accepted because metrics and logs are implemented, distributed tracing is NOT: the OTel exporter stays disabled and the otel-collector / Loki / Tempo block in observability/compose.yaml stays commented out on purpose (the collector image is not published for this milestone), so no trace exists to measure — the t86 sweep scanned metrics, logs, and the tree, and recorded that it cannot measure what does not run; the same gap is disclosed in observability/README.md and observability/collector.yaml, and in security/ai-tool-data-policy.md | Implement the tracing pipeline as its own card (publish the collector, uncomment the compose block, wire the exporter), then measure spans and drop this row |
