All commands run from the repository root in WSL bash and are exit-code based,
non-interactive, and network-free. Environment notes (Builder and Verifier):

- `export PATH="$HOME/.local/bin:$PATH"` makes the Linux `uv` binary
  (`~/.local/bin/uv`) resolvable; `command -v …|| exit 1` turns a missing
  toolchain into a clear fail instead of a 127.
- node/npm are **Windows** binaries on this WSL host (t2 precedent): plain
  `npm` from a WSL shell fails. The Makefile frontend recipes therefore must
  detect WSL (`test -e /proc/sys/fs/binfmt_misc/WSLInterop`) and invoke
  `cmd.exe /c "cd /d $(shell wslpath -w <frontend-dir>) && <command>"`,
  with a plain `cd frontend && …` fallback for non-WSL hosts. This was
  proven feasible against the merged t2 suite (vitest 3/3 green via
  `make test-frontend`, eslint+tsc green via `make lint-frontend`).
- ac2's `grep -qP "^\t…"` checks anchor toolchain delegation to **recipe
  lines** (tab-indented), so a mention in a comment cannot satisfy it.
  `make -n` alone is NOT sufficient for target presence: GNU make exits 0 for
  a name listed only in `.PHONY`, hence the `^target[[:space:]]*:` grep.
- All six ACs fail pre-implementation on current main (verified: ac1 lacks the
  app vars, ac2–ac4 have no Makefile, ac5 has no LICENSE, ac6's README is one
  line). There is no lint-style non-regression-only AC here; the lint runs in
  ac3/ac4 are gated behind Makefile existence, so they fail pre-implementation
  too (t3 precedent note satisfied in the other direction).

**Environment discovery baked into the ACs:** `make` is GNU Make 4.3 (WSL),
but npm/node are Windows binaries — a naive `cd frontend && npm test` recipe
fails on this host (t2 groom recorded the same for direct npx). The proven
pattern (tested against the merged t2 suite during this groom: vitest 3/3 and
eslint+tsc green through a WSL-aware Makefile) is a `FE` macro that expands to
`cmd.exe /c "cd /d $(shell wslpath -w <abs frontend dir>) && …"` under WSL and
to `cd frontend && …` elsewhere. Note `$(CURDIR)`/`$(abspath …)` must resolve
to the repo's own `frontend/` (in a worktree that is the worktree path, which
is correct). Backend recipes need no such shim (`uv` is a Linux binary at
`~/.local/bin`).

**REQ-DOC-051 target list** (`dev, down, test, test-backend, test-frontend,
e2e, lint, migrate, seed, security`) plus the plan's `setup` and the
per-stack splits give the 17 targets ac2 pins. `migrate`/`seed`/`e2e`/
`security`/`down` are stubs until their phases — the targets exist now so
documented commands never dangle (Chapter 15 §15.8 is about the command
surface, criterion 14).

**README scope split (deliberate, not silent):** full REQ-DOC-010 compliance
(15 sections incl. live-demo URL, criteria-mapping table, agent-pack notes)
is impossible in phase 1 — there is no deployment, no openapi.yaml, no agent
pack yet. ac6 gates the reproducibility core (prereqs → cp .env → make setup
→ dev → test → lint → license) and leaves the polish pass to phase_8_docs,
which owns the criteria-mapping table and live-demo link.

Contract-first note: `contract_first.require_for` is `[backend, api, database]`;
