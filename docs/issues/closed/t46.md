# t46 - E2E startup unblock: runtime uv-cache ownership (Dockerfile) and compose CORS_ORIGINS JSON form

## Context

E2E has never passed. Every run dies at "Wait for the health endpoint" because the app
container exits within ~1 s of start. Platform #49 was opened with the MEASURED uv-cache
root cause (orchestrator, docker 29.8.2, MAIN 99d9975). The groom then reproduced the
whole startup chain in this worktree and found the container carries THREE stacked
blockers, not one; the supervisor ruling (Option B) scopes t46 to the first two, which
are both runtime startup CONFIG files, and defers the third (Postgres migration
portability) to t47.

**GROOM MEASUREMENTS at base 7c8f929 (this worktree, docker 29.8.2, everything below
executed - nothing fabricated):**

- **Finding 1 - the #49 root cause, CONFIRMED at base.** `docker compose up -d --build`
  -> app container Exited(2) in <1 s; app logs exactly
  `error: Failed to initialize cache at /tmp/uv-cache` /
  `Caused by: failed to open file /tmp/uv-cache/sdists-v9/.git: Permission denied (os error 13)`;
  `curl http://localhost:8000/api/v1/health` rc=7 (connection refused) on all 30 probes
  over the full 60 s window. Mechanism: `ENV UV_CACHE_DIR=/tmp/uv-cache` + build-time
  `RUN uv sync --frozen --no-dev` run as ROOT create a root-owned cache subtree; the
  runtime CMD (`uv run alembic ... && uv run uvicorn ...`) runs as `app` and cannot
  initialize it. Fix (measured): `RUN mkdir -p /tmp/uv-cache && chown -R app:app /tmp/uv-cache`
  placed after the build-time uv sync and before `USER app` -> cache error GONE, container
  proceeds into alembic.
- **Finding 2 - compose CORS_ORIGINS is not valid JSON (NEW, measured this groom).**
  With the Dockerfile fix applied, the container dies again, now inside alembic env.py:
  `pydantic_settings.exceptions.SettingsError: error parsing value for field "CORS_ORIGINS"
  from source "EnvSettingsSource"`. Cause: `docker-compose.yml` sets
  `CORS_ORIGINS: http://localhost:5173` (plain string) while `Settings.CORS_ORIGINS` is
  `list[str]`; pydantic-settings 2.x JSON-decodes complex fields BEFORE field validators
  run, so the `_split_cors_origins` validator never sees the value. Measured locally with
  the real Settings class: the plain string raises SettingsError; the quoted JSON form
  `'["http://localhost:5173"]'` parses to `['http://localhost:5173']` rc=0. The JSON form
  is the documented shape (docs/requirements/Chapter14_CICDandDeployment.md line ~432 uses
  exactly `CORS_ORIGINS: '["http://localhost:5173","http://localhost:8000"]'`). Fix: change
  EXACTLY that one line in docker-compose.yml. It cannot be fixed from the Dockerfile -
  compose `environment:` overrides image ENV.
- **Finding 3 - the Postgres migration path has never worked (measured; DEFERRED to t47).**
  With fixes 1+2 applied, alembic reaches Postgres and fails: `psycopg.errors.DatatypeMismatch:
  column "is_active" is of type boolean but default expression is of type integer` -
  `001_initial_schema.py` uses `server_default=sa.text("1")` and `002_categories.py`
  `sa.text("0")` on BOOLEAN columns (SQLite-isms). An in-image probe with those two patched
  advanced the failure to `005_budgets`: `CHECK (year_month GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]')`
  (`YEAR_MONTH_FORMAT_CHECK_SQL`, backend/app/models/budget.py:48) is SQLite-only GLOB
  syntax Postgres rejects; and `backend/tests/integration/test_budget_migration.py:143`
  ASSERTS the GLOB DDL text, so the portability fix must also update the pinned 270-test
  suite. This is why t46 CANNOT honestly gate on health-ok: health can only go green after
  the t47 migration-portability card. t46 kills findings 1+2; t47 kills finding 3 and
  closes the E2E-green path.
