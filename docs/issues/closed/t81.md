## Context

**What this card is.** Criterion 13 asks for an AI-driven incident response.
An AI analysis is an uncheckable claim until something can reject a bad
answer, so this card ships the two artifacts that make the claim checkable:
the prompt an AI on-call is given (`responder-task.md`) and the JSON Schema
its answer must validate against (`response.schema.json`), plus the pinned
validator command (`validate_response.py`) that decides accept/reject. t84
is what produces a real `response.json`; this card is the contract it is
graded against, and it ships no incident record, no policy and no runbook.

**W3 disposition (the plan-review finding this groom was required to
resolve).** The survey draft named the validator
`incident-response/validate_response.mjs` in Constraints while its own
pinned-command reasoning reached for a JSON Schema library by `node`, and
the phase_13 plan pointer for this card names
`incident-response/validate_response.py (validator/test leg)` - one
artifact, two extensions, which is exactly the W3 ambiguity the review
