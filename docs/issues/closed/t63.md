# t63 - README Quick Start made npm-first: check / setup:local / dev / stop as the primary operator path, make demoted to an Alternative section, Stopping and Troubleshooting added (Windows-11-first, all-English, Docker banned)

## Context

This card is the operator-facing half of `phase_10_operator_ux`. The platform issue (#69) carries
the operator ruling referred to here as **Q1a**: the README is the operator's daily surface, the
operator box is **Windows 11 with no `make`**, and therefore the four npm commands that t62 landed
must become the FIRST and PRIMARY path in the README, with `make` demoted to an Alternative section.

t60 and t62 are both closed and merged, so the commands this card documents already exist and are
already proven. The four ROOT scripts are `npm run check`, `npm run setup:local`, `npm run dev` and
`npm run stop`, implemented by `scripts/dev/{common,check,setup,dev,stop}.ts` (node builtins only,
zero new dependencies). The README must describe them as they actually behave - every behavioural
claim fenced below is corroborated against the merged helper source, not against prose.

The carried README (308 lines, cr-stripped sha256 `a64efaa2...`) fails that test on four counts,
each measured rather than asserted:

- its Quick Start IS the make path - `make setup`, `make dev-backend`, `make dev-frontend` - and
  there is no npm quick start at all, so an operator with no `make` has no first command to type;
- its Prerequisites section lists GNU make as a requirement, which on the operator box is a wall
  (ac4 makes the demotion explicit and requires the section to say make/bash are NOT needed);
- it has no section telling the operator how to STOP the stack, and no troubleshooting surface, so
  the two failure modes an operator actually hits (ports already in use, and a WSL-created
  `backend/.venv` that `npm run check` repairs on Windows) are undocumented;
- it still carries 10 lines of non-ASCII residue (em-dashes), while Q1a says the operator surface is
  all-English (ac5 fences pure ASCII, which is why that leg is RED at base rather than a no-op).

**The pin doctrine (Q1a, and the reason this card looks unusual).** The README is byte-pinned as
pin-2 (`a64efaa2...`, 308 lines) inside stored gates - `tests[227]` and others replay it - and those
pins are hard-pinned in `docs/state/merge_test_index.json`. This card MUST NOT and DOES NOT demand
that the current stored pins stay green after its own merge: **pin-2 retires at t63's merge**, and
t64's composite carries `tests[227]` as a NAMED EXCLUSION. What this card does instead is fence the
NEW README by STRUCTURE and BEHAVIOUR (sections present, npm-first ordering, all-English, Stopping
section, troubleshooting rows, make demoted), and publish the cr-stripped sha256 of the intended
final bytes as a **pin-3 CANDIDATE, disclosure only**. The orchestrator appends pin-3 to the index at
merge time from the MERGED bytes; this card never opens the index (the index is in the FORBIDDEN set
and ac6 fails if the delta names it). No AC asserts an exact final line count as a pass condition;
ac6 bounds the README to the stored 30..500 window instead, because the only line-count claim this
card can legitimately pin is one measured from its own seeded bytes (367 lines), and pinning it would
make an innocent later edit a false RED.

One environment fact is fenced rather than assumed, because it is the single most likely way this
card breaks on a clean checkout: stored gates `tests[128]` and `tests[201]` match command lines via a
character class that includes a trailing carriage return, so they pass **only while the working-tree
README keeps CRLF endings**. ac6 therefore requires CRLF working bytes. Measured on this seeded
final: stored gates 27, 119, 128, 135, 144 and 201 all GREEN; only `tests[191]` (already stale
before this card) and `tests[227]` (pin-2, expected to retire) go RED.
