## Goal

Build the two security primitives the auth service (t8) composes: a password
module (passlib bcrypt rounds=12 hash/verify plus a dummy verify enabling the
REQ-BE-032 timing mitigation) and a JWT module (python-jose HS256 create/decode
with the full claim set and fixed-algorithm validation). Pure unit-testable
modules — no FastAPI, no DB — so the security-critical logic is locked down
with tests before endpoints exist. This is the crypto half split out of the
plan's template 2 so endpoint wiring (t8) stays inside the file/AC limits.

## Acceptance criteria

- [ ] ac1 — `backend/app/auth/password.py` exposes `hash_password(plain: str) -> str` and `verify_password(plain: str, hashed: str) -> bool` backed by a passlib `CryptContext(schemes=["bcrypt"], bcrypt__rounds=12)`. Three unit tests prove: (a) `hash_password` output starts with the literal `$2b$12$` identifier, is exactly 60 chars, and hashing the same input twice yields two DIFFERENT strings (automatic per-hash salt); (b) `verify_password(plain, hash_password(plain)) is True` and `verify_password("wrong-passphrase", hash_password(plain)) is False` — explicit `is True` / `is False`, so a truthy non-bool or an over-broad pass cannot satisfy it; (c) `verify_password("anything", "not-a-bcrypt-hash") is False` and `verify_password("anything", "") is False` — malformed stored hashes return False and never raise (only passlib's specific `UnknownHashError` may be caught; `except Exception` is forbidden). (REQ-BE-030, REQ-SEC-020.)
- [ ] ac2 — `backend/app/auth/password.py` exposes `verify_dummy(plain: str) -> None` that runs a full bcrypt verification against a fixed dummy hash so an unknown-user login costs the same as a wrong-password login (REQ-BE-032/REQ-SEC-023). The unit test: hashes a reference password, times one real `verify_password` call, times one `verify_dummy("any-guest-input")` call, and asserts the dummy call (i) does not raise, (ii) evaluates to `None` per its declared contract (asserted via `assert verify_dummy(...) is None` — see the mypy note in Verification commands: the Builder may satisfy the same contract with a call statement plus a `is None` assertion written so mypy strict accepts it), (iii) took at least 0.05 s (a real cost-12 cycle, not a no-op stub), and (iv) took no more than 10x the real-verify elapsed time (timing parity — a dummy that verifies at a different cost fails). (REQ-BE-032, REQ-SEC-023.)
- [ ] ac3 — `backend/app/auth/jwt.py` exposes `create_access_token(subject: str) -> str` (subject = user id string) producing a python-jose HS256 JWT signed with `settings.JWT_SECRET`. Two unit tests prove: (a) decoding the token with the settings secret (via python-jose directly) yields EXACTLY the claim set `{sub, iss, aud, iat, exp, type}` — `set(claims) == {...}` equality, so extra or missing claims fail — with `sub` equal to the passed subject, `type == "access"`, `iss == JWT_ISSUER`, `aud == JWT_AUDIENCE`, and `exp - iat == JWT_ACCESS_TOKEN_EXPIRE_MINUTES * 60` (1440 * 60 = 86400, the 24-hour REQ-BE-023 window); (b) `jose_jwt.get_unverified_header(token) == {"alg": "HS256", "typ": "JWT"}` AND `jose_jwt.decode(token, "the-wrong-secret", algorithms=["HS256"], audience=..., issuer=...)` raises `jose_jwt.JWTError` (wrong-secret rejection is proven at the library level here; the module-level path is ac4's `test_decode_rejects_wrong_secret`). Tests pin JWT settings via a `monkeypatch.setenv` + `get_settings.cache_clear()` fixture (t5/t6 tmp-isolation precedent) — no `.env` file, no committed secret. (REQ-BE-020, REQ-BE-023, REQ-ARCH-040.)
- [ ] ac4 — `backend/app/auth/jwt.py` exposes `decode_access_token(token: str) -> dict[str, Any]` that validates signature, expiry, audience, issuer, and `type == "access"`, always passing `algorithms=[settings.JWT_ALGORITHM]` explicitly (never read from the token header — REQ-BE-022), and raises its OWN typed `TokenError` (defined in `app/auth/jwt.py`, extending `Exception` specifically) on any failure; t8 maps it to 401. Eight unit tests: valid token round-trips returning claims with `sub`; and each of the seven reject paths raises `pytest.raises(TokenError)` — wrong secret (token forged with `attacker-secret`), tampered signature (flip a signature character), EXPIRED token, wrong audience, wrong issuer, `type == "refresh"`, and a manually forged `alg=none` token (hand-built base64url header/payload, empty signature). The expiry test is deterministic WITHOUT sleeps or freezegun: it monkeypatches `JWT_ACCESS_TOKEN_EXPIRE_MINUTES=-1`, clears the settings cache, issues the token through `create_access_token` itself (so `exp` is strictly in the past at decode time) — no time travel library, no wall-clock wait. Each reject path is a SEPARATE named test node (no over-broad parametrized blob), and all assertions pin `TokenError` specifically, not `Exception`. (REQ-BE-021, REQ-BE-022, REQ-SEC-021.)
- [ ] ac5 — Non-regression, quality gates, and the dependency pin that makes the stack actually work on this host: from `backend/`, `uv run pytest -q` exits 0 (t1/t3/t5/t6 tests plus the 14 new unit tests), `uv run ruff check .` exits 0, `uv run mypy .` (strict) exits 0; AND `pyproject.toml` declares a `bcrypt` pin (line matching `^\s*"bcrypt[>=<]`) AND `uv.lock` resolves `bcrypt` to a 4.0.x version. Rationale (probed on merged main @ 5db0621): passlib 1.7.4's import-time bcrypt backend probe calls `bcrypt.hashpw` with a > 72-byte password, which bcrypt 5.0.0 (the version current `uv.lock` resolves) rejects with `ValueError: password cannot be longer than 72 bytes` — with bcrypt 5.x pinned, EVERY password test errors at collection. The lock change is pre-authorized (REQ-TECH-080): add `bcrypt>=4.0,<4.1` to `dependencies`; bcrypt 4.0.1 was proven against passlib 1.7.4 in this groom's reference run (hash/verify/dummy all clean, `$2b$12$` output). Note bcrypt >= 4.1 < 5 emits a non-fatal `AttributeError ...__about__` log from passlib but functions; the pin excludes it anyway. (REQ-TECH-023, REQ-TECH-080.)

## Constraints

- python-jose only (REQ-TECH-023); do NOT add PyJWT. passlib only for bcrypt; do not call the `bcrypt` package directly (passlib's context owns the policy and the dummy hash).
- The ONLY dependency edit allowed is adding `bcrypt>=4.0,<4.1` to `backend/pyproject.toml` `[project] dependencies` and committing the regenerated `backend/uv.lock` (bcrypt 5.0.0 -> 4.0.1; REQ-TECH-080). No other package may move in the lock — re-verify with `uv lock --check` after editing.
- The JWT module must not import FastAPI, HTTPException, SQLAlchemy, or `app.models` — it raises its own `TokenError` (extending `Exception`, caught specifically, never `except Exception`) so t8 can map failures; keep it unit-testable in isolation.
- The password module must not import anything from `app.*` (pure crypto); the JWT module may import only `app.config.get_settings`.
- `verify_password` returns False (never raises) for malformed hash inputs; catch only `passlib.exc.UnknownHashError` (optionally also `passlib.exc.SecurityError` if encountered — note `SecurityError` does NOT exist in passlib 1.7.4's `exc` module; the actual name is `PasslibSecurityError`).
- No hardcoded secrets: tests pin JWT settings via `monkeypatch.setenv` + `get_settings.cache_clear()` (fixture teardown must clear the cache again); never create `backend/.env`, never commit a real secret (REQ-TECH-091). The dummy bcrypt hash (if the Builder materializes one instead of using `CryptContext.dummy_verify()`) is a decoy and must be documented as such.
- Files: exactly `backend/app/auth/password.py`, `backend/app/auth/jwt.py`, `backend/app/auth/__init__.py` (re-export/docstring only), `backend/tests/unit/test_password.py`, `backend/tests/unit/test_jwt.py`, plus the two-file dependency pin (`backend/pyproject.toml`, `backend/uv.lock`). Nothing else — `config.py`, `database.py`, `main.py`, models, migrations, `tests/unit/test_config.py`, `tests/unit/test_user_model.py`, Makefile, `.env.example` stay untouched.
- Python style per coding_standards.md: 4-space indent, snake_case modules, PascalCase classes, Google docstrings, complete annotations (mypy strict), specific exceptions only. Test naming: `test_<module>.py`, `class Test<Module>`, `test_<action>_<expected>`; the 14 node IDs in Verification commands are contractual.
