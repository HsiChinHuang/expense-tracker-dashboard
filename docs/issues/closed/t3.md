## Goal

Implement the public health check endpoint `GET /api/v1/health` returning
`status`, `database`, `fallback_active`, and `version`, with an integration
test, so deployment monitoring (REQ-TECH-062 UptimeRobot pings, Render health
checks in phase_5) has a target and the response contract of
Chapter 7 §7.2.1 is locked in before the DB/fallback wiring arrives.

Implemented as `backend/app/routers/health.py` registered in `create_app()` under the `/api/v1` prefix. ## Context

This is the health-check issue from `docs/plan.md` § phase_1_init (fourth
template; plan files: `backend/app/routers/health.py`,
`backend/tests/test_health_api.py`). It implements FR-HEALTH-1
(REQ-PROD-016) and the Chapter 7 §7.2.1 `HealthResponse` contract, and gives
phase_5 (Render health checks, UptimeRobot pings per REQ-TECH-062,
`ops/health-check.md`) an endpoint to point at.

Path deviation from the plan template: the test lives at
`backend/tests/integration/test_health_api.py`, not `backend/tests/test_health_api.py`,
because t0's Chapter 16 structure (REQ-STRUCT/REQ-ARCH-052) established
`backend/tests/unit/` and `backend/tests/integration/` and t1's smoke test set
the precedent of `tests/unit/`. The plan's file list is superseded by the
merged structure.

**Scope tension (deliberate, not silent)**: FR-HEALTH-1 says `status = "ok"`
when the database is reachable and `"degraded"` when fallback is active, and
Chapter 13 §13.2.2 shows `"version": "1.0.0"`. Full fidelity requires the
database session (phase_2) and the SQLite fallback (phase_5, REQ-PROD-017),
neither of which exists after t1 — t1 explicitly deferred DB wiring. Phase 1
therefore delivers the contract skeleton: the endpoint exists, is public, and
returns the four fields with the documented schema and honest static values
(`fallback_active: false`, `status: "ok"`, configured `database`, real app
version). ac3 pins exactly this so the Builder is not tempted to invent DB
wiring, and phase_5 re-grooms the semantics when fallback lands. The version
must be the app's own version string (currently `0.1.0`), not the doc example
`1.0.0`.

Contract-first verification applies (`contract_first.require_for` includes
`backend`/`api`), so every AC has a runnable node-ID-pinned command.

- Structured JSON logging of health pings (REQ-ARCH-060, phase_5 ops work).

- Metrics, rate limiting, or auth on the health route — FR-HEALTH-1 is explicitly public.
