## Goal

Add the dedicated cross-resource security suite
`backend/tests/integration/test_isolation.py` (plus a small money-precision
module if groom splits it) that exercises the MERGED t11/t13/t14 endpoints as
a black box with two real users (A and B) and real JWTs: B can never read,
list, update, or delete any of A's expenses, budgets, or custom categories;
B can never attach an expense to A's custom category; system categories are
usable by both and immutable for both; and money survives the full HTTP→DB→
HTTP loop as exact 2-decimal Decimals with string transmission. This is a
tests-only issue: if a test finds a real defect, the defect is fixed inside
this issue's scope (test + minimal service fix), never papered over.

### Contradiction flagged for groom (KEY FINDING — do not silently "fix")

The body's **ac3** says money must round-trip `"updates through
9999999999.99"`. That value **cannot round-trip** on the merged contract:

- `backend/app/schemas/expense.py:41`, `backend/app/schemas/budget.py:33`,
  `backend/app/services/expense_service.py:46`,
  `backend/app/services/budget_service.py:61` all pin
  `AMOUNT_MAX = Decimal("999999999.99")` (9 integer digits), and
  `backend/app/models/expense.py` / `budget.py` use `sa.Numeric(12, 2)`.
- Chapter 5 §5.11.2 is the authoritative per-layer statement —
  `NUMERIC(12,2)` / `condecimal(max_digits=12, decimal_places=2)` → capacity
  999,999,999.99. Chapter 7 §7.10.1's `Max value 9999999999.99` (and Chapter 8
  §8's `parseFloat(v) <= 9999999999.99` FE snippet) is **internally
  inconsistent with its own `max_digits=12`** — 10 integer digits need
  `NUMERIC(14,2)`.
- The merged, already-merged-and-indexed behaviour rejects over-max: t13 ac2 /
  t14 ac2 pin `"10000000000.00"` → 422 `INVALID_AMOUNT` field `amount`
  (both nodes are in `docs/state/merge_test_index.json`). Chapter 12 and
  Chapter 2 §2.4.3/§2.4.4 state only "Decimal everywhere, NUMERIC(12,2)" and
  "max 12 digits, 2 decimals" (§12.5.2) — i.e. they support the merged
  capacity, not the §7.10.1 number.
- **Suggested resolution (pinned in ac3 above, direction only — groom
  ratifies):** round-trip through `AMOUNT_MAX` itself (`"999999999.99"`), and
  pin `"9999999999.99"` as the **over-max 422 `INVALID_AMOUNT`** case. The body
  checkbox text is left intact with an inline amendment note so the intent
  ("exercise the top of the range") is preserved and the contradiction stays
  visible.
- This is a **spec-vs-merged-contract** ambiguity, not a production bug: no
  production change is warranted, and changing `AMOUNT_MAX` would re-open the
  merged t13/t14 contracts (out of t15's scope per W16).
