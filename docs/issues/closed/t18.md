## Goal

Ship the two remaining CRUD pages on t16 hooks and t17's toast/confirm
patterns: `budget_page.tsx` (month picker drives `use_budget`; set/edit form
with Zod-validated amount; delete with confirm; a 12-month history list
composed client-side by querying the per-month endpoint for the trailing 12
months — the GET-absent-"0.00" contract makes this cheap and phase_4 does NOT
own it) and `categories_page.tsx` (system section rendered read-only with no
delete control; custom section with create form and delete-with-confirm, 409
duplicate/in-use errors surfaced per field/row). Routes `/budgets` and
`/categories` wired into the protected tree with unique titles. This closes
the milestone's frontend scope.

## Context

t18 is the last card of phase_3_crud (9/9). t16 delivered the data layer
(`api/budgets.ts`, `api/categories.ts`, `hooks/use_budget.ts`,
`hooks/use_categories.ts`, counted MSW handlers in `src/test/handlers.ts`);
t17 delivered the UI conventions this card reuses verbatim (ToastProvider,
ConfirmDialog, the RHF + hand-rolled `zodResolver`/`applyApiErrors` modal
pattern, the inline `role="status"` / `role="alert"` + Retry / `<p>` empty
state presentation, and the "render the API money STRING verbatim" rule).
Nothing new is invented here: budgets are a per-month UPSERT (PUT by
`year_month`, so "create" and "edit" are the SAME mutation
`use_budget_mutations(ym).set`) and the category router exposes only
GET/POST/DELETE (there is NO category rename/update endpoint and there must
not be one — REQ-SEC-033). The 12-month history has no backend list endpoint
(Chapter 7 §7.6 exposes only the per-month trio), so it composes from the
per-month contract: 12 mounted `use_budget(ym)` observers, every one of which
is a prefix member of `queryKeys.budgets.root` and is therefore invalidated by
any set/remove — that single fact is both the ac1 "refetches the month"
mechanism and the ac2 history-refresh mechanism.
