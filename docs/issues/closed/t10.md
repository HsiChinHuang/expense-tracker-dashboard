## Context

t11 (categories API) cannot exist without a `categories` table, and t12's
audit revision needs the Alembic chain to have advanced to `002`. This issue
lands the whole persistence vertical for categories in one slice:

1. `backend/app/models/category.py` — the SQLAlchemy 2 `Category` model on
   the shared `Base` that t6 introduced in `app/models/user.py`.
2. `backend/alembic/versions/002_categories.py` — hand-written revision
   `002` (`down_revision = "001"`, the single head on main today) creating the
   table, its two CHECK constraints and its three indexes.
3. `backend/app/scripts/seed.py` — the single seed routine holding the ten
   Chapter 5 §5.9.1 rows, called as a data step from revision `002`.

Merged reality this issue is groomed against (main @ 52ef22f):

- `backend/app/database.py` (t5) exposes `create_db_engine` (SQLite
  `PRAGMA foreign_keys=ON` per connection), `create_session_factory` and
  `get_db`. It contains **no `create_all()` call and no startup/lifespan
  hook** — there is nowhere to hang a seed trigger.
- `backend/alembic/env.py` (t5/t6) is ONLINE-ONLY and builds its engine from
  `get_settings().DATABASE_URL`, so `DATABASE_URL=sqlite:////tmp/...` drives
  the CLI exactly as t6's ac2 already exploits. `alembic.ini` sets
  `script_location = alembic` and `prepend_sys_path = .`, which is why a
  revision module may `import app.*` (probed on a scratch tree: a probe
  revision importing an app module upgraded with rc=0).
- `backend/app/models/__init__.py` re-exports `Base`/`User`; t6's merged
  `tests/unit/test_user_model.py` asserts `set(Base.metadata.tables) ==
  {"users"}`, which necessarily fails once `Category` registers — see
  Constraints for the mandatory one-line amendment.
- Baseline on main: `uv run pytest` → 53 passed; ruff and mypy strict clean.
  Expected after t10: 65 passed (12 new nodes).
- Seed-trigger ruling (review_plan W15b, pinned): the trigger is the
  **Alembic data step** in revision `002`, because that is the only trigger
  the merged code can support (no `create_all()` seam exists in
  `database.py`, and adding an app-startup hook would be a phase_2 module
  refactor with no REQ in t10's scope). Chapter 5 §5.9.3's "SQLite after
  `create_all()`" row is satisfied by tests calling the same routine directly.
- Layout deviation recorded (W15b): §5.10.2's idealized layout is
  `001_initial_schema` (all five tables) + `002_seed_categories` (data only).
  The merged project ships one incremental revision per vertical slice (001 =
  users only), so this revision is named descriptively `002_categories` and
  carries both the category DDL and the seed data step.

- SQLite is the dev/test engine. The REQ-DB-021 color CHECK is written with
  portable string functions, because SQLite has no `~` regex operator
  (`color ~ '^#[0-9A-Fa-f]{6}$'` is PostgreSQL-only):
  `length(color) = 7 AND substr(color, 1, 1) = '#' AND
  rtrim(upper(substr(color, 2)), '0123456789ABCDEF') = ''`. It accepts
  `#EF4444`/`#abcdef` and rejects all four pinned bad values (probed on SQLite
  3.45.1). Express it ONCE in `app/models/category.py` as a module constant and
  import it into the revision so model and migration cannot drift.
- The partial unique index must be expressed for BOTH dialects:
  `sqlite_where=sa.text("user_id IS NOT NULL")` AND
  `postgresql_where=sa.text("user_id IS NOT NULL")` (verified to emit
  `CREATE UNIQUE INDEX ... WHERE user_id IS NOT NULL` on SQLite).
- Index/constraint names follow Chapter 5 §5.8.1/§5.8.2 verbatim:
  `idx_categories_user_id`, `idx_categories_is_system`,
  `idx_categories_user_name_unique`, `ck_categories_color_format`,
  `ck_categories_system_consistency`.
- No raw SQL outside the migration (REQ-TECH-031); UUID PKs generated in
  Python (REQ-TECH-032, t6 precedent) — no `gen_random_uuid()` server default.
- `is_system` uses `server_default=sa.false()` and `created_at` uses
  `server_default=sa.func.now()` (both compile to valid DDL on SQLite and
  PostgreSQL — probed); the revision may mirror them with `sa.text("0")` /
  `sa.text("CURRENT_TIMESTAMP")` as t6's 001 does.
- `TIMESTAMPTZ` (REQ-DB-020) is unavailable on SQLite; use `sa.DateTime` +
  server default exactly as t6's `User` does and record it as a documented
  simplification (phase_5_infra owns PostgreSQL engine selection).
- The seed module must NOT import ORM models and must NOT commit; it takes a
  `Connection` and returns the number of inserted rows.

## Builder traps (discovered by probing the merged environment)

- Import order in `alembic/versions/002_*.py` must be
  `import sqlalchemy as sa`, blank line, then `from alembic import op` and the
  `app.*` imports in the same block (ruff I001; t6 hit the same rule).
- In `app/scripts/seed.py` the stdlib `uuid` import belongs in the FIRST block
  (`import uuid` before `from typing import ...`), otherwise ruff I001.
- mypy strict: `Category.__table__` is typed as `FromClause`; use
  `cast(Table, Category.__table__)` and `cast(String, col.type).length` (t6's
  precedent). A `CheckConstraint` name is `str | None` → cast it.
- `pragma foreign_key_list(categories)` returns
  `(id, seq, table, from, to, on_update, on_delete)` — the local column is index
  3 and `on_delete` is index 6; asserting index 2/5 compares against
  `'users'`/`'NO ACTION'` (both reproduced as failures during this groom).
- `alembic_version` DOES appear in `sqlite_master` after a CLI/API migration
  run (probed), so the post-migration table-set assertion must be
  `{"users", "categories", "alembic_version"}`.
- `uv run alembic heads` does not create or touch the database even though
  `env.py` is online-mode (probed: no file created, rc=0 even with an
  unreachable directory) — safe to call inside the pinned command.
- Do not add dependencies: `pyproject.toml` and `uv.lock` must stay
  byte-identical (SQLAlchemy 2.1.3 / Alembic 1.20.0 already resolve).
