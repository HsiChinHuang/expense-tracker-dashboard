## Goal

Write the two files that make the operational loop ALERT-DRIVEN instead of
hand-run: the Prometheus scrape configuration for this repo's local backend,
and `observability/alerts.yaml`, which is the SINGLE SOURCE OF TRUTH for every
alert name and metric name referenced anywhere else in this milestone. If a
name is not in `alerts.yaml`, it does not exist in this milestone.

## AC draft (groom will fence these - target 5 fenced ACs, inside max_acs=6)

- **ac1 - both files exist and parse under a pinned self-contained validator.**
  `prometheus.yml` parses as YAML and has a `scrape_configs` block that
  includes the local backend target and the Prometheus self-scrape;
  `alerts.yaml` parses as YAML and has a `groups` block. The validator is a
  `python3 -c` / `node -e` parse of the committed bytes - no Docker, no
  `promtool` download, no network.
- **ac2 - the two required alerts exist with the required shape.** `alerts.yaml`
  defines `HighExpenseCreationFailures` (business metric, a threshold AND a
  `for:` duration, annotations `service`, `environment`, `version`, `owner`
  and a dashboard URL) and `DBFallbackActive` (condition = health degraded /
  `fallback_active` sustained for 5m). The fence asserts both names, the
  `for:` durations, and every named annotation key. Negative control: an alert
  with no `for:` must fail the leg.
- **ac3 - the metric names it references are declared, and it is the only
  place they are declared.** Every metric name appearing in any `expr` is
  listed in a machine-readable inventory block in the same file (a commented
  or an `annotations`-carried list is acceptable, but it must be greppable),
  so t77/t79/t83/t85 can extract from one place. The fence extracts the expr
  metric names and asserts the set is a subset of the inventory.
- **ac4 - the alert that the incident record will quote is byte-stable.** The
  `DBFallbackActive` entry is a self-contained YAML object that t83 can copy
  verbatim into `alert.json`; ac4 pins its exact serialised form (key order and
  values) so a later card's byte-copy has something fixed to match, and states
  that any change to it forces a t83/t84 re-check.
- **ac5 - delta purity.** Only `observability/prometheus.yml` and
  `observability/alerts.yaml` are added; `observability/README.md`,
  `observability/compose.yaml` (t75's files), `docker-compose.yml`, `backend/`,
  `openapi.yaml`, `README.md` and every `docs/` file are byte-clean against the
  immutable ref named in the card; the purity leg is declared non-appendable if
  it pins the branch base.

## Constraints (hard)

- Exactly 2 files: `observability/prometheus.yml`, `observability/alerts.yaml`.
- `alerts.yaml` is the ONE alert-name and metric-name authority for the
  milestone. This card invents names; no other card may.
- No new port, no new service, no edit to `observability/compose.yaml` (if the
  rule-file mount is missing, the card reports it as a follow-up rather than
  editing t75's file - a second writer on one file is the phase_12 lesson).
- Scrape targets are loopback only (`127.0.0.1:8137` for the backend,
  `127.0.0.1:9090` for self-scrape). No remote scrape target, no cloud
  exporter, no hosted Grafana.
- `for:` durations are stated in seconds/minutes explicitly; the 5m figure for
  `DBFallbackActive` is the operator-approved value and the fence pins it.
- No live Prometheus/Alertmanager execution in any fence; no network call; no
  dependency addition.
- `openapi.yaml` untouched. The `/metrics` endpoint this scrape config reads is
  t78's, and its contract exemption is recorded in t78's card text, not here.
