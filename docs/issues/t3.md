## Goal

Implement the public health check endpoint returning `status`, `database`,
`fallback_active`, and `version`, with an integration test, so deployment
monitoring (REQ-TECH-062 UptimeRobot pings) has a target and the DB-fallback
state is observable before phase_5.

## Acceptance criteria (draft)

- [ ] `GET /api/v1/health` returns 200 without authentication (public).
- [ ] Response body contains exactly the fields `status`, `database`, `fallback_active`, `version` (REQ-PROD-016).
- [ ] `database` reports the active database backend; `fallback_active` is a boolean that is `false` in normal local operation (real fallback logic arrives in phase_5 / REQ-PROD-017).
- [ ] Response is validated by a Pydantic 2 response model (REQ-TECH-022).
- [ ] Integration test via FastAPI TestClient asserts status code and all four fields (at least 1 test per AC).

## Dependencies

- t1 (backend skeleton with app factory, pytest, and TestClient smoke test).

## Constraints

- Route registered under the `/api/v1` prefix.
- SQLAlchemy/engine access only, no raw SQL (REQ-TECH-031).
- `except Exception` is forbidden; error handling must be specific (coding_standards.md).
