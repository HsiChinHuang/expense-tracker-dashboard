## Goal

Add the dedicated cross-resource security suite
`backend/tests/integration/test_isolation.py` (plus a small money-precision
module if groom splits it) that exercises the MERGED t11/t13/t14 endpoints as
a black box with two real users (A and B) and real JWTs: B can never read,
list, update, or delete any of A's expenses, budgets, or custom categories;
B can never attach an expense to A's custom category; system categories are
usable by both and immutable for both; and money survives the full HTTP→DB→
HTTP loop as exact 2-decimal Decimals with string transmission. This is a
tests-only issue: if a test finds a real defect, the defect is fixed inside
this issue's scope (test + minimal service fix), never papered over.

## Acceptance criteria

- [ ] ac1 — Expense isolation matrix (user B vs resource of user A): GET list never contains A's rows; GET by id → 404; PUT → 404 and A's row unchanged; DELETE → 404 and A's row still present; 404 bodies are byte-identical for unknown-id vs other-user-id (no existence leak, REQ-SEC-031).
- [ ] ac2 — Budget + category isolation: B's GET of A's budgeted month returns the "0.00" absent-shape, never A's amount; B cannot DELETE A's budget (404, budget intact); B's category list excludes A's custom categories; B cannot DELETE A's custom category (404); B creating an expense with A's custom `category_id` → 404 and no row written (REQ-SEC-032); system categories are listable/usable by both users and reject DELETE/POST-name-collision for both (REQ-SEC-033).
- [ ] ac3 — Money precision: an expense of `"0.10"` + updates through `"9999999999.99"` and `"0.01"` round-trip byte-exact as 2-decimal strings through POST → GET → PUT → list; aggregation-safe (values are Decimal in the service — asserted via a service-level unit test summing Decimal strings, no float artifacts like `0.30000000000000004`); budget amount `"1234.56"` round-trips identically (REQ-DB-090, REQ-SEC-050, REQ-PROD-023).
- [ ] ac4 — Audit observability from outside: after the matrix runs, every successful expense/budget CREATE/UPDATE/DELETE has a matching audit_logs row for the correct user (and none for the other user), and the app exposes no audit endpoint (openapi grep) (REQ-PROD-015, REQ-SEC-034 completion).
