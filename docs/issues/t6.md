## Metadata

- Milestone: phase_2_auth
- Requirements: REQ-DB-010 (users table: id UUID PK, email VARCHAR(255) UNIQUE NOT NULL indexed, username VARCHAR(50) UNIQUE NOT NULL, hashed_password VARCHAR(255) NOT NULL, is_active BOOLEAN NOT NULL default true, created_at/updated_at timestamps), REQ-DB-011 (email unique + case-insensitive, username unique + case-sensitive, password never plaintext, is_active=false blocks login but preserves data), REQ-SEC-020 (hashed_password column stores bcrypt hashes; no plaintext), REQ-SEC-052 (UNIQUE on email, username), REQ-TECH-032 (UUIDs generated in Python for SQLite portability), REQ-TECH-031 (SQLAlchemy only), REQ-PLAN-020 (phase 2 task 2.1: user model + migration)
- Source: requirements/Chapter5_DatabaseDesign.md §5.3.1, §5.3.4; requirements/Chapter12_SecurityandAudit.md §12.3.1

## Goal

Define the SQLAlchemy 2.0 `User` model and the first Alembic revision so the
`users` table exists with the Chapter 5 §5.3.1 shape on both SQLite (dev) and
PostgreSQL (later), with the migration chain started at a single named
revision. Passwords are representable only as hashes (`hashed_password`);
hashing itself is t7's job — this issue only makes the table and model correct.

## Acceptance criteria

- [ ] ac1 — `backend/app/models/user.py` defines a SQLAlchemy 2.0 declarative `User` (PascalCase per coding_standards.md) mapped to table `users` with columns exactly: `id` (UUID primary key, generated in Python via `uuid.uuid4` default so SQLite works — REQ-TECH-032), `email` (VARCHAR(255), unique, not null, indexed), `username` (VARCHAR(50), unique, not null), `hashed_password` (VARCHAR(255), not null), `is_active` (Boolean, not null, default true), `created_at` and `updated_at` (timestamp with server defaults). No plaintext password column exists anywhere. (REQ-DB-010.)
- [ ] ac2 — Alembic revision `001` (filename starting `001_`) exists under `backend/alembic/versions/`, is autogenerate-free (hand-written `upgrade()`/`downgrade()`), creates the `users` table with the ac1 columns/types/constraints, and from `backend/` `uv run alembic upgrade head` exits 0 against the default SQLite URL; `uv run alembic downgrade base` then `upgrade head` again also exits 0 (reversibility). The `alembic_version` row exists after upgrade.
- [ ] ac3 — Case-insensitive email uniqueness holds at the service-independent level required by REQ-DB-011: the model or a unit test demonstrates that uniqueness is enforced (SQLite: the UNIQUE constraint on the normalized value; the Builder MUST document in a docstring that email normalization to lowercase happens in the service layer, t8 — the DB layer enforces uniqueness on whatever is stored). Username uniqueness (case-sensitive) is enforced by the UNIQUE constraint; a unit test inserts two users with duplicate email (same case) and asserts an `IntegrityError`.
- [ ] ac4 — `updated_at` refreshes on update: a unit test creates a user, updates `username`, commits, reloads, and asserts `updated_at >= created_at` (server onupdate behavior present); `is_active` defaults to `True` on insert without being passed.
- [ ] ac5 — No regression and quality gates: `uv run pytest` exits 0 (t1/t3 tests plus new model tests all green), `uv run ruff check .` exits 0, `uv run mypy .` (strict) exits 0 in `backend/`. `create_app()` still boots (importing models must not break the health endpoint tests).

## Constraints

- SQLAlchemy 2.0 style only (`Mapped` / `mapped_column`, `DeclarativeBase` established in t5); no legacy 1.x `column()`/`declarative_base()` patterns (REQ-TECH-021).
- UUID generated in Python, not by DB-specific functions (`gen_random_uuid()` is PostgreSQL-only and forbidden — REQ-TECH-032). Use `sa.Uuid` (SQLAlchemy 2.0 generic UUID type) or `Uuid(as_uuid=True)` with a Python default; do not use `postgresql.UUID` directly.
- Timestamps must work on SQLite: use `DateTime` with `server_default=func.now()` / `onupdate` semantics that function on both backends (t5's engine is SQLite for dev/test; TIMESTAMP-with-tz fidelity on SQLite is a known storage simplification — document it, do not invent SQLite-specific hacks).
- Only the `users` table in this issue: categories/expenses/budgets/audit_logs tables are phase_3_crud scope (REQ-DB-020 … 040) and MUST NOT be created here; the 001 revision is scoped so later revisions chain cleanly.
- No bcrypt/passlib usage, no auth endpoints, no schemas — t7/t8 own those.
- Files touched MUST stay within the plan file list (model + migration + tests); adding `backend/app/models/__init__.py` re-exports is fine.
