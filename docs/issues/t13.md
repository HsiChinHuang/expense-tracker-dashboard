Contract pins taken from the chapters (the REQs are terse; the chapters are
the tie-break, all re-read during groom):

- **Expense representation (Chapter 7 §7.5.1 `ExpenseResponse`) — FROZEN at
  exactly ten keys**: `id` (UUID string), `amount` (string,
  pattern `^[0-9]+\.[0-9]{2}$`, e.g. `"125.50"`), `currency` (`"USD"`),
  `category_id` (UUID string), `category_name` (string), `category_color`
  (HEX string), `date` (`"YYYY-MM-DD"`, `format: date`, NO timezone —
  REQ-SEC-051), `note` (string|null), `created_at`, `updated_at`
  (date-time strings). The nine non-`note`/`updated_at` keys are
  `required`; the merged response model always emits all ten, so tests
  assert the key set is EXACTLY these ten for POST 201, GET 200, PUT 200
  and every list `items[]` element.
- **Create body (§7.5.2 `CreateExpenseRequest`)**: required
  `{amount, category_id, date}`, optional `note` (≤ 500); `amount` is a
  STRING matching `^[0-9]+(\.[0-9]{1,2})?$`. `currency` is not a client
  field — the service fixes `"USD"` (REQ-DB-030/034); a body that sends
  `currency: "EUR"` is rejected 422 (REQ-PROD-031 "currency ≠ USD").
- **Update body (§7.5.4 `UpdateExpenseRequest`)**: all four fields optional,
  `minProperties: 1` — i.e. PUT is partial-capable per the chapter, which
  CORRECTS the survey's "full replacement" wording; an empty body `{}` is
  422, and every supplied value is validated by the same rules as create.
- **Status codes (§7.5.1..§7.5.5 + Appendix B)**: list 200/422 only (an
  out-of-range page is therefore 200 with `items: []`, never 404); POST
  201/404/422; GET 200/404; PUT 200/404/422; DELETE 204/404. Cross-user
  access is 404, never 403 (REQ-SEC-031/032).
- **Error-code split (Chapter 2 §2.5.2 vs the merged handler)**: the five
  amount-VALUE cases (`"0"`, `"-1"`, three decimals, over
  `9,999,999,999.99`, `""`) are **422 `INVALID_AMOUNT`, field `amount`**
  (Chapter 2 §2.5.2's table verbatim — the reason Appendix B defines
  `INVALID_AMOUNT` at all); every other body/query validation failure
  (missing `amount` key, missing `category_id`, malformed date, note > 500,
  `currency` ≠ USD, `page`/`page_size`/`year_month` out of range) is
  **422 `VALIDATION_ERROR`** through the merged `RequestValidationError`
  handler. One frozen rule per case; the Builder may reach it however it
  likes (e.g. `amount: str` + explicit conversion raising
  `AppError(422, INVALID_AMOUNT, field="amount")`).
- **404 codes**: bad/foreign/unknown `category_id` on POST/PUT → 404
  `CATEGORY_NOT_FOUND` field `category_id` (t11's validator, unchanged);
  unknown/other-user expense id → 404 `NOT_FOUND` field `null` (Chapter 6
  §6.8.3's `AppError("NOT_FOUND", "Expense not found", 404)`).
- **Service shape (Chapter 6 §6.8.1..6.8.6)**: `create_expense` validates
  the category, `db.add` + `db.flush()` (id without committing), writes the
  audit row, then a SINGLE `db.commit()` + `refresh`; `list_expenses`
  filters `user_id`, applies `year_month` as a half-open month range
  (`date >= start, date < end`), applies `category_id`, orders
  `date DESC, created_at DESC`, offsets/limits, and returns
  `(items, total)`; `get_expense` filters `user_id`; `update_expense`
  re-validates a changed `category_id` and audits old+new; `delete_expense`
  audits old value only. The service commits exactly once per request
  (REQ-ARCH-023).
- **Decimal discipline (Chapter 5 §5.11.2/§5.11.3, REQ-SEC-050,
  REQ-TECH-022)**: `Numeric(12, 2)` in the model, `decimal.Decimal` in
  Python, string on the wire; SQLite stores `Numeric` as REAL, so reads are
  coerced back to `Decimal` and compared only after
  `quantize(Decimal("0.01"))`. No float may appear in a service function or
  a response body.
- **Constraint/index names (Chapter 5 §5.5.2/§5.5.3) — FROZEN**: CHECKs
  `ck_expenses_amount_positive` (`amount > 0`) and
  `ck_expenses_currency_usd` (`currency = 'USD'`); indexes
  `idx_expenses_user_id` (user_id), `idx_expenses_user_date`
  (user_id, date DESC), `idx_expenses_user_category` (user_id, category_id),
  `idx_expenses_category_id` (category_id). FKs: `user_id` →
  `users.id` `ondelete="CASCADE"`, `category_id` → `categories.id`
  `ondelete="RESTRICT"`.
