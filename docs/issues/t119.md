## Goal

The CI/CD grading dimension tops out at 3 only when there is CD to dev **and** a manual
production deploy. The project has automatic CD (`deploy.yml` fires on a green E2E
`workflow_run`) and no dev environment, so the honest claim is 2/3 (t114 records it).
The operator's strategy is "stable 2 + fight for 3": claim 2/3 **and** ship the real
manual pipeline so the missing half is a documented design choice rather than an
absence.

This card ships that pipeline: one file, `.github/workflows/promote.yml`, that a human
triggers from the Actions tab, that pauses on the GitHub **Environment `production`**
required-reviewer gate (created by the operator in repository Settings, therefore not
visible in git), and that then performs the same two steps `deploy.yml` already
proves: POST the deploy hook taken from the existing `RENDER_DEPLOY_HOOK` secret, and
verify `/api/v1/health` with the same bounded retry loop.

**What this card must NOT do, stated up front because the temptation is exactly where
the failure would be:** it does not create a second Render service, a second database,
or a dev environment, and it must never be described - here or in the scoring map - as
if it did. There is ONE live service and the promote path deploys to that same service;
the human gate is real, environment separation is not. And it writes exactly one file:
the three existing workflows stay byte-identical, and the index legs the new file
breaks are **priced in writing and left to the orchestrator**, not quietly edited.

**Honesty rule (binding on the prose this card writes into the workflow's comments):**
every statement must be checkable by a reader in 30 seconds at the named entry point -
which for a workflow file means the YAML itself. No comment may claim a second
environment, a staging instance, or an approval mechanism that the file does not
reference.

## The specification this card ships

`.github/workflows/promote.yml`, complete write surface, satisfying every line below
(ac1 greps them mechanically):

```yaml
# .github/workflows/promote.yml - manual, human-gated production deploy.
# One service exists: this deploys the SAME live Render service that deploy.yml's
# automatic CD already targets. The human gate is the GitHub Environment
# 'production' (required reviewers, configured in repository Settings, not in git);
# environment separation does NOT exist. Hook URL from the RENDER_DEPLOY_HOOK
# secret only (REQ-CICD-070); least-privilege token (REQ-CICD-071).
name: Promote

on:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  promote:
    environment: production
    runs-on: ubuntu-latest
    steps:
      - name: Trigger the Render deploy hook
        env:
          RENDER_HOOK: ${{ secrets.RENDER_DEPLOY_HOOK }}
        run: |
          if [ -z "$RENDER_HOOK" ]; then
            echo "RENDER_DEPLOY_HOOK secret is not configured"
            exit 1
          fi
          curl -fsS -X POST "$RENDER_HOOK"

      - name: Verify the deployed health endpoint
        env:
          APP_HEALTH_URL: ${{ secrets.RENDER_APP_URL }}
        run: |
          for i in $(seq 1 30); do
            if curl -fsS "$APP_HEALTH_URL"; then
              echo "deploy verified: health endpoint is ok"
              exit 0
            fi
            sleep 10
          done
          echo "health endpoint never turned ok after the deploy"
          exit 1
```

Design notes the builder must preserve: no `push`/`pull_request`/`schedule` trigger
(the whole point is that nothing fires this automatically); no `secrets:` block
redeclaring anything; no new secret name; no `environment_url`/`environment:` value
other than `production`; the health loop byte-isomorphic to `deploy.yml`'s so one
contract is expressed one way twice rather than two subtly different ways; and comments
that state the single-service truth rather than implying a staging tier.
