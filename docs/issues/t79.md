**The named mechanism.** Three counters and one callback gauge are declared ON t78's
SUBSTRATE, in `backend/app/telemetry.py`, inside `setup_telemetry`'s provider block, on a
second instrumentation scope. `setup_telemetry` is idempotent (its guard returns before
constructing a second provider), so instruments registered there are registered exactly once
per process and `create_app()` remains the single wiring point - this card adds NO call-site
to `backend/app/main.py`. The services then increment through a substrate helper
(`get_business_counter(name)`) that returns a counter from the business scope; OTel
`create_counter` is a get-or-deduplicate lookup by name, so call-site construction costs one
dict hit and the services never restate a metric string - they import the module constants.
The gauge is an `create_observable_gauge` whose callback returns
`[Observation(1 if is_fallback() else 0)]`, so the value is computed at SCRAPE time from the
one latch the process already owns; nothing caches it, nothing re-probes the database, and
`backend/app/database.py` is not edited.

groom in the shared bucket venv registered a counter named
`expense_created_total` and an observable gauge named `db_fallback_active` through
`PrometheusMetricReader` and rendered the exposition with `generate_latest`; the output
lines were `expense_created_total{otel_scope_name="t79.probe",...} 1.0` and
`db_fallback_active{otel_scope_name="t79.probe",...} 1.0` - the names survive the
OTel-to-Prometheus mapping unchanged, so the alert rule and the exposed series really are
the same string. The same probe surfaced the one real trap in this mechanism: a callback that
returns a bare `Observation` fails with `TypeError: 'Observation' object is not iterable`
inside the SDK and the series silently disappears from the exposition. The callback MUST
return a LIST of observations, which is what the pinned live-latch node proves end to end.
