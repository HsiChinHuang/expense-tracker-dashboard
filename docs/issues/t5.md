## Goal

Replace the phase_1 placeholder state (DATABASE_URL is only an `.env.example`
line; no settings, no engine, no Alembic runtime wiring) with the database
foundation every later issue needs: a Pydantic Settings object reading the
Chapter 3 §3.10 variables, a SQLAlchemy 2.0 engine + session factory with the
SQLite PRAGMA handling, a working Alembic setup (`alembic upgrade head` runs
against `sqlite:///./dev.db` by default), and the t4 `make migrate` stub wired
to the real command. This is the database half of `docs/plan.md` § phase_2_auth
template 1, split off so t6 can land the User model on a clean migration chain.

Tests `tests/unit/test_config.py::TestSettings::test_env_var_overrides_default` (monkeypatch/`env` kwarg override beats the default) and `TestSettings::test_defaults_match_env_example` (defaults equal the values parsed from `.env.example`) pass.
- [ ] ac2 — `Settings` enforces REQ-BE-012: when `ENVIRONMENT == "production"`, construction fails (a validation error — `ValidationError`/`ValueError`, not a silent fallback or a warning) if `JWT_SECRET` is empty or the placeholder `"change-me"`; in `development` the same placeholder is allowed. - [ ] ac3 — `backend/app/database.py` provides `create_db_engine(...)` and a session factory whose `get_db()` yields a `Session` per request and closes it in a `finally` block (REQ-BE-040/REQ-ARCH-022). Integration tests `tests/integration/test_database.py::TestDatabase::test_get_db_yields_and_closes_session` (generator yields a `Session`, closes it on normal completion and on consumer-side exception) and `TestDatabase::test_sqlite_pragma_foreign_keys_enabled` (`SELECT PRAGMA foreign_keys` via a session from the factory returns `1`) pass against a tmp-file SQLite URL injected through the `DATABASE_URL` env var — `backend/dev.db` is never touched.
- [ ] ac4 — Alembic is wired: `backend/alembic.ini` and `backend/alembic/env.py` exist and are tracked (replacing the current `backend/alembic/versions/.gitkeep`-only tree), `env.py` reads `DATABASE_URL` from the app settings with no hardcoded URL, and from `backend/` `uv run alembic upgrade head` exits 0 with zero revisions against the URL provided via `DATABASE_URL` (a tmp-file SQLite path in the verification command, so `backend/dev.db` stays untouched). A placeholder-first migration chain is NOT required (t6 adds revision 001); this AC proves the harness runs. `alembic upgrade head` must actually connect (engine/configure before `run_migrations`), so the SQLite file is created — a no-connection early exit that merely prints "Can't locate revision" is not acceptance.
- [ ] ac5 — The root `Makefile` `migrate` target (currently the t4 echo-only stub at line ~73) is a real recipe that runs `uv run alembic upgrade head` in `backend/`: a `^migrate[[:space:]]*:` rule exists, `make -n migrate` exits 0, a tab-indented recipe line contains `uv run alembic upgrade head`, and `make migrate` actually exits 0 while driving Alembic against the `DATABASE_URL` from the caller's environment (the command pins a tmp path under the gitignored `build/` and requires the file to exist afterwards — proving the recipe wired settings → alembic → DB end-to-end rather than echoing). The recipe must not hardcode a DB path and must not require a `backend/.env` file. (REQ-DOC-051 completion of the t4 forward-delegation.)
- [ ] ac6 — No regression: from `backend/`, `uv run pytest` exits 0 with the pre-existing tests (t1 smoke + t3 health) still passing, `uv run ruff check .` exits 0, and `uv run mypy .` (strict) exits 0. Notes for Builder and Verifier (all probed on current main during this groom):

- **Test isolation (t5/t6/t8 constraint).** ac3 and ac4 pin tmp-file SQLite
  URLs (`/tmp/t5_ac3.db`, `/tmp/t5_ac4.db`); ac5 pins `build/t5_ac5.db` (under
  the gitignored `build/`). Nothing in these commands can touch
  `backend/dev.db`, and no shared state persists between ACs (each `rm -f`s its
  own file). The absolute `sqlite:////tmp/...` form is deliberate — a relative
  `sqlite:///./t.db` would land in `backend/`.
- **ac2 needs no real secret.** The command prefixes
  `env JWT_SECRET=change-me ENVIRONMENT=development`, so the production-refusal
  branch is exercised purely by the test constructing
  `Settings(environment="production", ...)` with the placeholder visible; no
  production secret is required anywhere. The `ENVIRONMENT=development` pin
  neutralizes a machine-level `ENVIRONMENT=production` so the dev-branch test
  cannot flake on operator env.
- **ac1/ac2 env hygiene.** `backend/.env` must NOT be created by this issue
  (out of scope). Verified during groom: the repo-root `.env` holds only
  launcher vars (PLATFORM/API_TOKEN/REPO_ID/MAX_SLOTS) and pytest runs with
  cwd `backend/`, so no app-variable `.env` can shadow the defaults the
  `test_defaults_match_env_example` test asserts against.
- **ac4 asserts the connection happened.** Groom probe with alembic 1.20.0:
  an `env.py` that only imports `context` exits 0 with zero revisions WITHOUT
  ever connecting (no DB file created). The `test -f /tmp/t5_ac4.db` half of
  the command rejects that degenerate wiring; `env.py` must build the engine
  and `context.configure(connection=...)` before `run_migrations()` (standard
  online-mode template) so the SQLite file is created even at zero revisions.
  Current main fails ac4 at rc=1 (the `test -f alembic.ini` guard; bare alembic
  fails rc=255 `No 'script_location' key found`) — verified. Tracking of the
  two files is a Definition-of-Done item; the command deliberately avoids git
  (WSL worktree gitdir pointers are unresolvable — Verifier shim precedent).
- **ac5 pins the recipe contract, not prose.** `grep -qP "^\t…"` anchors
  `uv run alembic upgrade head` to a tab recipe line (t4 precedent: comments
  cannot satisfy it, and `make -n` alone passes for `.PHONY`-only names, hence
  the `^migrate[[:space:]]*:` grep). The real `make migrate` run with
  `DATABASE_URL` pointing at `build/t5_ac5.db` plus the post-run `test -f`
  proves the recipe delegates to alembic end-to-end; the current echo-only
  stub fails this half deterministically (echo never creates a file) even
  though `make -n migrate` exits 0 on main. The recipe must honor the caller's
  `DATABASE_URL` (via `env.py` → app Settings, REQ-ARCH-061 env wins), not a
  hardcoded path.
- **ac6 is a pure non-regression gate** and therefore passes on current main
  (verified rc=0: 3 tests passed, ruff clean, mypy strict clean). This is
  intentional and stated in the t3-precedent style: t5's new tests raise the
  collected count but the AC only requires exit 0 + the pre-existing t1/t3
  tests still green.
- `export PATH="$HOME/.local/bin:$PATH"` makes the Linux `uv` binary
  resolvable (t1..t4 precedent); `command -v … || exit 1` turns a missing
  toolchain into a clear fail instead of a 127. t5 is backend-only: no

- Verifier: run `uv sync` in `backend/` first if the worktree venv is cold

  bucket hash changes — expect a fresh bucket or the per-worktree fallback).
