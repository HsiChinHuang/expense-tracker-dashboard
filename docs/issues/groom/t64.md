## Context

depends on t60, t61, t62 and t63, all four are closed and merged, and what it does is attest, at one
commit, that the conjunction of everything they and their predecessors established is true at this
tree. That distinction drives every fence below: an exit card may not smuggle in a fix, so anywhere
this groom found a defect it records the defect and names a follow-up card instead of editing the
surface (see **Discovered defects** in the Definition of Done).

Five criteria, each one deterministic `bash -c` one-liner, each carrying its negative control INSIDE
the same fence so a run that prints GREEN also prints the proof that the leg bites.

the same sequential protocol and measured 2773 s (~46 min) for `required=223 skipped=14 failed=0`, so
budget ~50 minutes for the composite leg alone. Nothing here is
estimated: every timing quoted is a measured run on this tree.

**The venv-flavour fact (measured, and the reason ac3 is written the way it is).** WSL `uv run`
REBUILDS `backend/.venv` in place when the interpreter flavour does not match the host: measured on
this tree, a win32-native venv (`Scripts/python.exe` present) was replaced by a WSL venv
(`bin/python`, `pyvenv.cfg home = /usr/bin`) by a single `uv run pytest` of stored entry tests[9].
Since 92 of the 223 mandatory replay entries invoke `uv run`, **ac1's composite necessarily leaves a
WSL-flavoured venv**, and a subsequent `npm run dev` on Windows then dies with `spawn ENOENT` on
`backend\\.venv\\Scripts\\python.exe`. The README's troubleshooting row tells the operator to run
`npm run setup:local` in exactly that situation, and that is the correct remedy for a BARE tree
(measured: fresh `setup:local` on win32 -> `sys.platform=win32`, `dev.db` migrated to `005 (head)`,
`elapsed=9`), but it is NOT sufficient when a WSL venv already exists, because `venvPresent()` in
`scripts/dev/common.ts` tests only `pyvenv.cfg` and `setup:local` then prints "already present -
reusing it (Q6 repair-without-destruction)" and fails later on the same ENOENT. ac3 therefore proves
the operator path by detecting the flavour mismatch and applying the reset that works TODAY
the fence removes the wrong-flavour `backend/.venv` (a disposable build artifact, rebuilt by `setup:local` in ~9 s) and re-runs the documented setup, printing both steps - and the defect is recorded
as a follow-up card rather than fixed here.

**What this card does NOT do.** It appends ZERO index entries and publishes NO pin-4: the README
digest churn is precisely the staleness class this milestone is closing, so pinning a new digest would
perpetuate it. It touches no product code, no test file, no manifest, no CI file, no container surface.

## Replay protocol for ac1 (read this before running it)

1. **Run from the repo root of a post-merge tree with a clean working tree.** ac1 asserts
   `count=237`, the tests[227] digest `8cbb4722...` and `tests[231].issue_id == t63` before it runs a
   single entry, so a stale or reordered index stops it rather than misleading it.
2. **The git shim is part of the fence.** Several stored entries (e.g. tests[139], tests[230]) invoke
   `cmd.exe /c "git -C <WinPath> ..."`, which does not resolve inside a linked worktree unless
   `GIT_DIR`/`GIT_WORK_TREE` are exported. ac1 defines a `git` function over
   `GIT_DIR="$GD" GIT_WORK_TREE="$PWD"`, `export -f git`, and sources each entry through a
   `/tmp/t64_ac1_wrap.sh` wrapper that re-exports it. Measured: tests[139] is rc=1 with zero output
   bare and rc=0 under the shim - that difference is the whole reason 139 is a *name-only-environment*
   exclusion rather than a regression.
3. **.env-free tree.** The replay assumes no `backend/.env`/`frontend/.env` overrides, matching the
   stored gates' own assumption.
4. **Budget ~50 minutes.** The pre-repair replay measured 2681 s over 237 entries (222 GREEN / 15 RED); the
   definitive post-repair composite measured **2773 s (~46 min)** for `required=223 skipped=14 failed=0`. The
   honest planning number is ~50 minutes. The
   per-entry cap is 900 s. Do not "optimise" by running entries in parallel: several of them own
   ports, `docs/criteria` or `backend/dev.db`, and the sequential order is what makes a RED
   attributable.
5. **`docs/criteria` is regenerated in place by the matrix entries.** ac1 restores it at the end with
   `cmd.exe /c "git -C <WinPath> checkout -- docs/criteria"`. ac2 does the same.
6. **The venv ends up WSL-flavoured.** 92 of the mandatory entries invoke `uv run`, and WSL `uv run`
   rebuilds `backend/.venv` for its own host. Run ac1 BEFORE ac3, or let ac3 do its own venv-flavour reset,
   which it performs itself (delete the wrong-flavour venv, then `npm run setup:local`) and prints as
   evidence. ac4's mypy leg has the same effect as ac1's (measured: after ac4, `backend/.venv/bin` exists
   and `Scripts/python.exe` does not), which is why the documented order for this card is ac1, ac2, ac4,
   ac5 and then ac3 LAST.
7. **A RED outside the 14 named classes is a regression.** Do not add a disposition to make it pass;
   that is how a stale-pin milestone silently becomes a green-lie milestone. Fix the cause or file the
   card.
