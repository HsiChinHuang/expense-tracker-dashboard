# t62 - npm-script dev workflow in ROOT package.json: check (Q6 auto-fix) / setup:local / dev / stop (Windows-11-first, node builtins only, zero new deps, Docker banned)

## Context

This card is the operator-ux spine of phase_10. The platform issue (#68) carries five operator
rulings, referred to here as Q1-Q5, plus two standing constraints from the phase_10 review (W6, W7)
and one measured budget (W8). In plain terms: an engineer who has just cloned this repository on a
Windows 11 laptop must be able to reach a running, clickable environment with **four npm commands
typed in the ROOT of the checkout** - `npm run check`, `npm run setup:local`, `npm run dev`,
`npm run stop` - and must never need Docker, a Linux VM, a WSL shell, or a hand-written shell
invocation to get there.

Why the ROOT manifest, and why the word ROOT is repeated. The repository already carries a
`Makefile` (blob `55745c4d`, cr-stripped `701979ef`) that is the Linux/WSL path and is owned by the
carried t53 line; it is not this card's surface and this card does not touch it. The frontend
manifest `frontend/package.json` is **byte-frozen** at cr-stripped sha256
`e3f7f5862beefd98957a3b951d6791714d528e53e5a887f1715c2c680ddd1b62` (blob `1f210a29`) by the W6 pin,
so the four new scripts cannot live there either. That leaves exactly one legal host for the
workflow: the ROOT `package.json`, which is **not** frozen. ac6 asserts both pins on every run, so
the envelope this card may edit is measured rather than trusted.

The script contract is pinned to four exact lines, because a workflow that is only described in
prose is not a workflow:

| script | pinned command |
| --- | --- |
| `check` | `tsx scripts/dev/check.ts` |
| `setup:local` | `tsx scripts/dev/setup.ts` |
| `dev` | `tsx scripts/dev/dev.ts` |
| `stop` | `tsx scripts/dev/stop.ts` |

Why `.ts` helpers under `scripts/dev/` and not `.mjs` next to them. The ROOT manifest is
`type=module` and the ROOT tooling already lints and type-checks `scripts/**/*.ts`: the ROOT
`tsconfig.json` (blob `5f4ec030`, cr-stripped `e383c536`) includes `scripts/**/*.ts`, and the ROOT
lint command is `eslint launcher extensions scripts --ext .ts`. A `.ts` helper under `scripts/dev/`
is therefore checked by the existing strict TypeScript config and the existing eslint baseline with
no configuration change at all - which is precisely the W7 requirement. A `.mjs` helper would sit
outside both globs and satisfy nothing; ac1 counts plain-JS files under `scripts/dev/` and fails if
there is even one, so the escape route is closed rather than discouraged.

Environment facts measured for the fences, disclosed because they shape what can be proven
mechanically. The executor is WSL bash driving **win32** processes through `cmd.exe`; win32 node is
v24.16.0 and `tsx` 4.23.15 is present in the ROOT `node_modules`. All git metadata reads go through
`cmd.exe /c "git -C <win-path> ..."` because the worktree's `.git` pointer holds a Windows path that
WSL git cannot resolve. The ROOT `node_modules` inside a worktree is a **symlink** to the main
checkout, so no fence may delete through it and none does. Vite binds `[::1]` only, so the frontend
probe is `http://localhost:5173/` and never `127.0.0.1`; the port scan is `netstat -ano` without the
`-p tcp` filter so IPv6 listeners are not missed. Seeded control listeners are spawned as
**win32-native** processes (`Start-Process` on a win32 python) so that netstat reports a real, distinct
owning PID - a WSL-seeded listener appears under the shared relay PID and would weaken the
report-the-PID leg, which is why ac2 and ac5 both seed natively.

The one thing this card cannot prove mechanically, stated plainly. On win32 a real console Ctrl+C
cannot be delivered from this harness: `process.kill(pid, "SIGINT")` maps to TerminateProcess, so the
handler never runs, and `SIGBREAK` is unsupported (ENOSYS). The graceful-teardown contract is
therefore pinned two ways instead of being skipped: at the **source level** (ac4 requires
`process.on("SIGINT")` and `process.on("SIGTERM")` registration in `scripts/dev/dev.ts`) and at the
**outcome level** (ac4 requires zero listeners left on 8000/5173 after teardown, and ac5 makes
`stop` the guaranteed reaper for whatever a killed-or-crashed `dev` left behind). The human act of
pressing Ctrl+C is disclosed as a manual Definition-of-Done check rather than pretending to be
automated.

Fence shape, and why three of these six are GREEN at base. ac1, ac2, ac3, ac4 and ac5 are RED at
base for the reason this card exists: the four scripts are absent, so every lifecycle leg fails at
the manifest. ac6 is GREEN at base by construction - it attests that the envelope is respected - and
a green-at-base fence is exactly where a false attestation hides, so it carries a seeded negative
control that fires in the same run (a one-character tamper of the byte-pinned manifest, which the
same digest function must reject). Every other fence carries its own seeded control: a type-broken
helper and an unused-var helper inside the ROOT tooling (ac1), a sentinel file proving the venv was
present and two win32-native listeners proving foreign ports are reported not killed (ac2), a
script-reported `elapsed=` token parsed against the W8 budget (ac3), live health and proxy probes
plus a post-teardown port count (ac4), and an unrelated 8799 listener that must **survive** the
reaper (ac5). A control that fails to fire turns its fence RED rather than passing silently.

  unused-var helper) fire inside the same run so neither ROOT-tooling leg is vacuous.

  win32-native control listeners seeded on ports 8799 and 15123 and a sentinel file planted inside a
  present `backend/.venv`, `npm run check` executes the SAME script natively on win32 through
  `cmd.exe` and prints `platform=win32` with `native=yes` (Q1: the same npm script must work on both

  survives - and leaves the carried frontend tree installed and resolvable (Q6 repair without
  destruction). The rebuild half of Q6 is executed by ac3.
- **ac3 - `setup:local` repairs a bare tree inside the W8 budget (Q5/Q6/W8).** With
  `backend/.venv`, `backend/dev.db` and `frontend/node_modules` moved aside, `npm run setup:local`

Residual risk disclosed up front. The first is the win32 signal gap described in Context: the
graceful-teardown handler path is pinned by source inspection and by post-teardown port state, so a
handler that is registered but wrong at runtime would be caught by the port-count leg only if the

sync about 11 seconds, alembic about 19 seconds, npm install about 92 seconds), so a first run on a
cold network with a slow mirror could approach the budget for environmental reasons; the fence
reports both the harness-measured and the script-reported elapsed values so a verifier can tell a
real overrun from a slow mirror. The third is prerequisite coupling: ac2, ac3 and ac4 need an
installed tree, and ac3 deliberately destroys and restores that state to prove the repair leg, so
the fences must be run in the stated order (ac1, ac2, ac6, ac3, ac4, ac5) and each prints its
