## Goal

Wire the complete backend auth vertical: Pydantic auth schemas, an auth service
(register/login with the timing-safe and lowercase-email rules), the
`get_current_user` FastAPI dependency, and the three endpoints
`POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `GET /api/v1/auth/me`
registered under `/api/v1` in `create_app()` — with the Chapter 7 error-code
contract. After this issue a real user can obtain and use a 24-hour JWT
against the SQLite dev database; t9 consumes these endpoints on the frontend.

## Acceptance criteria

- [ ] ac1 — `POST /api/v1/auth/register` with valid `{email, username, password}` returns 201 and a JSON user body containing `id`, `email`, `username`, `is_active`, `created_at` (and NOT `hashed_password` or any password field). Email is normalized to lowercase before storage (REQ-BE-050); the returned email is lowercase. Duplicate email returns 409 with `code == "DUPLICATE_EMAIL"`, `field == "email"`; duplicate username (case-sensitive) returns 409 `DUPLICATE_USERNAME` / `field == "username"`. Invalid body (bad email format, password < 8 or > 72 chars, username outside 3–50, username containing spaces) returns 422 with `code == "VALIDATION_ERROR"`. All error bodies use the `{detail, code, field}` shape. (REQ-API-020, FR-AUTH-1, REQ-PROD-030 subset, REQ-BE-031.)
- [ ] ac2 — `POST /api/v1/auth/login` with correct credentials returns 200 with exactly `access_token`, `token_type == "bearer"`, and a nested `user` object (no password fields); the access token decodes (per t7's `decode_access_token`) with `sub` equal to the user id. Wrong password returns 401 `code == "INVALID_CREDENTIALS"`; nonexistent email returns the SAME 401 code and body (no enumeration, REQ-SEC-022) and the service path runs the t7 dummy verify (REQ-SEC-023 — assert via spy/monkeypatch in a unit test). A user with `is_active = False` cannot log in: 401 `code == "USER_INACTIVE"`. (REQ-API-021, FR-AUTH-2, REQ-BE-051.)
- [ ] ac3 — `GET /api/v1/auth/me` with `Authorization: Bearer <valid token>` returns 200 with the current user's `id`/`email`/`username`/`is_active`. Missing header returns 401 `code == "UNAUTHORIZED"`; malformed or wrong-signature token returns 401 `TOKEN_INVALID`; expired token returns 401 `TOKEN_EXPIRED`; a valid-signature token whose `sub` references an `is_active = False` user returns 401 `USER_INACTIVE` (REQ-BE-041, REQ-ARCH-041, REQ-SEC-022). `get_current_user` lives in `backend/app/auth/dependencies.py` and is provided via FastAPI `Depends`.
- [ ] ac4 — The auth router is registered in `create_app()` under the `/api/v1` prefix (registration order health → auth per REQ-BE-141 intent), the OpenAPI schema at `/openapi.json` lists the three paths, and the whole flow works end-to-end against the SQLite test database inside one pytest integration module: register → login → me (happy path) plus the error paths of ac1–ac3, using `TestClient` and a per-test isolated database (fixture creating tables via metadata or alembic upgrade on a tmp file DB). t3's health tests and t1 smoke tests still pass.
- [ ] ac5 — Structured logging per REQ-BE-051/REQ-BE-122: a failed login logs an event WITHOUT the raw email (hashed or masked identifier) and never logs passwords or tokens; a successful login/register logs an auth event. Verified by a caplog-based unit test asserting the raw email string and password string do not appear in any log record. (If the JSON logging infrastructure (REQ-BE-120) is not yet present, stdlib `logging` with structured `extra` is acceptable in phase_2; the full JSON formatter is phase_5 ops scope — document in Context.)
- [ ] ac6 — No regression and quality gates: `uv run pytest` exits 0 with all suites, `uv run ruff check .` exits 0, `uv run mypy .` (strict) exits 0 in `backend/`. No `except Exception`; AppError-style specific errors only.
