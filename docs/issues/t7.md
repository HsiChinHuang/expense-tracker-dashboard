## Goal

Build the two security primitives the auth service (t8) composes: a password
module (passlib bcrypt rounds=12 hash/verify plus a dummy verify enabling the
REQ-BE-032 timing mitigation) and a JWT module (python-jose HS256 create/decode
with the full claim set and fixed-algorithm validation). Pure unit-testable
modules — no FastAPI, no DB — so the security-critical logic is locked down
with tests before endpoints exist. This is the crypto half split out of the
plan's template 2 so endpoint wiring (t8) stays inside the file/AC limits.

## Acceptance criteria

- [ ] ac1 — `backend/app/auth/password.py` exposes `hash_password(plain: str) -> str` and `verify_password(plain: str, hashed: str) -> bool` backed by passlib `CryptContext(schemes=["bcrypt"], bcrypt__rounds=12)` configured via code or `passlib.bcrypt` settings (REQ-BE-030/REQ-SEC-020). Unit tests: hash of the same input twice differs (automatic salt); `verify_password` true for the matching pair, false for a wrong password; the hash string starts with the bcrypt `$2b$12$` identifier (rounds 12 visible).
- [ ] ac2 — `backend/app/auth/password.py` exposes `verify_dummy(plain: str) -> None` (or equivalent documented name) that runs a bcrypt verification against a fixed dummy hash so unknown-user logins cost the same as wrong-password logins (REQ-BE-032/REQ-SEC-023). Unit test asserts it neither raises nor returns a truthy result for any input.
- [ ] ac3 — `backend/app/auth/jwt.py` exposes `create_access_token(subject: str) -> str` (subject = user id string) producing a python-jose JWT whose decoded payload contains exactly the claims `sub`, `iss`, `aud`, `iat`, `exp`, `type` with `type == "access"`, `iss`/`aud` from settings (`JWT_ISSUER`/`JWT_AUDIENCE`), and `exp - iat == JWT_ACCESS_TOKEN_EXPIRE_MINUTES * 60` (default 1440 = 24h). Signed HS256 with `settings.JWT_SECRET`. (REQ-BE-020, REQ-ARCH-040, REQ-BE-023.)
- [ ] ac4 — `backend/app/auth/jwt.py` exposes `decode_access_token(token: str) -> <claims or raises typed error>` validating signature, expiry, audience, issuer, and `type == "access"`, always passing `algorithms=[settings.JWT_ALGORITHM]` explicitly (never read from the token header — REQ-BE-022). Unit tests each reject path: tampered signature, expired token (short-lived fixture via monkeypatched expiry), wrong audience, wrong issuer, `type == "refresh"`, and a manually forged `alg=none` token — all rejected; a valid token round-trips and returns claims including `sub`.
- [ ] ac5 — No regression and quality gates: `uv run pytest` exits 0 (all prior tests + new unit tests), `uv run ruff check .` exits 0, `uv run mypy .` (strict) exits 0 in `backend/`. `python-jose` and `passlib[bcrypt]` are already declared in `pyproject.toml` (t1); if passlib requires a bcrypt-version pin to work on this host, the pin is committed in `pyproject.toml` + `uv.lock` (REQ-TECH-080) — note passlib 1.7.4 + bcrypt 4.x emits a non-fatal `error reading from process`-class warning on some versions; the Builder must land a combination whose tests pass cleanly.

## Constraints

- python-jose only (REQ-TECH-023); do not add PyJWT.
- The JWT module must not import FastAPI, HTTPException, or the DB layer — it raises its own typed error (extending `Exception`, specific — coding_standards.md forbids `except Exception`) or returns a discriminated result; t8 maps failures to the error-code table. Keep it unit-testable in isolation.
- No hardcoded secrets: defaults for tests come from settings defaults / env overrides in test fixtures, never a committed real secret (REQ-TECH-091).
- `verify_password` returns False (never raises) for malformed hash inputs; handle only the specific passlib exceptions (`UnknownHashError`, `SecurityError`), not `Exception`.
- Files: exactly `backend/app/auth/password.py`, `backend/app/auth/jwt.py` + their unit tests (`backend/tests/unit/test_password.py`, `backend/tests/unit/test_jwt.py`); `backend/app/auth/__init__.py` re-exports allowed.
- AC count at the max_acs=6-style bound (5 ACs); expected diff < 300 lines.
