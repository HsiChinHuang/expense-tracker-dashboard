## Goal

Create the incident directory contract and the ONE incident this milestone
reconstructs: `2026-10-17-db-fallback-01`. This card owns the incident-ID
constant and the directory skeleton; t84 fills the evidence/response/resolution
trio inside it. The alert that fired is not invented - `alert.json` is a
byte-copy of the `DBFallbackActive` entry of `observability/alerts.yaml`.

## Measured base state (measured at survey on 245cd49, re-measure at groom)

- `incident-response/` exists only after t80; `observability/alerts.yaml`
  exists only after t76. Both are deps for exactly that reason.
- t76's ac4 pins the serialised form of the `DBFallbackActive` entry precisely
  so that this card's byte-copy has a fixed thing to match. The copy is
  verified by EXTRACTION at verification time (read the entry from the t76
  file, compare to the committed `alert.json`), never by restating the entry's
  content into this card - the t74 ac3 extraction pattern.
- The ID grammar (`YYYY-MM-DD-<slug>-<NN>`) is defined here, once, and t84/t88
  obey it. The chosen ID `2026-10-17-db-fallback-01` is the operator-approved
  constant for the drill the t80 harness performs.

## AC draft (groom will fence these - target 4 fenced ACs, inside max_acs=6)

- **ac1 - the scaffold exists and the ID follows the declared grammar.**
  `incident-response/incidents/README.md` exists and states the grammar;
  `incident-response/incidents/2026-10-17-db-fallback-01/` exists with its
  `README.md`; the directory name matches the grammar the README declares
  (the fence runs the grammar as a regex over the directory name).
- **ac2 - alert.json is a verbatim copy of the t76 DBFallbackActive entry.**
  The fence extracts that entry from `observability/alerts.yaml` and compares
  it to the committed `alert.json` (after a normalising serialisation so key
  order/indentation is not a false failure), asserting equality. A hand-typed
  paraphrase FAILS this leg, which is the whole point.
- **ac3 - the directory contract names every artifact and its owner.** The
  incidents README lists `alert.json`, `evidence/`, `evidence.json`,
  `response.json`, `resolution.md` and states which card writes each (t80
  collects `evidence/`, t84 writes the trio, this card writes the two READMEs
  and `alert.json`), so a reviewer can tell an incomplete incident from a
  deliberately staged one. The fence asserts the five artifact names and the
  owner sentence for each.
- **ac4 - delta purity and single-writer discipline.** Only the three
  allow-listed files are added; `observability/` (including `alerts.yaml`),
  `incident-response/collect-evidence.sh` (t80's), `ops/`, `backend/`,
  `security/`, `README.md` and every `docs/` file are byte-clean against the
  named immutable ref. The card states that t84 may write ONLY inside this
  incident directory and may not edit either README or `alert.json`.

- Exactly 3 files: `incident-response/incidents/README.md`,
  `incident-response/incidents/2026-10-17-db-fallback-01/alert.json`,
  `incident-response/incidents/2026-10-17-db-fallback-01/README.md`.
- This card OWNS the incident-ID constant `2026-10-17-db-fallback-01`. No other
  card may define, rename or renumber an incident ID.
- `alert.json` is a COPY, never a paraphrase, never a superset. If the t76
  entry changes, this card's byte-copy and t84's record must be re-checked -
  the incidents README says so in one sentence.

  plausible-looking `evidence.json` in this card would be exactly the
  attested-by-reference failure mode this milestone exists to remove; the
  directory is deliberately incomplete and the README says which card completes
  it.
- No timestamps are invented. Any date in the scaffold is the operator-approved
  drill date in the ID, not a fabricated event timeline.
- No product-code change, no backend change, no `openapi.yaml` change, no
  Docker, no network call in any fence.
