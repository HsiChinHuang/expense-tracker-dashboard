## Goal

The five committed reports describe the tree they were cut on, not the tree
this milestone leaves behind (t78/t79 added backend dependencies and code).
Re-run all five against the final merged tree so the security half of criterion
13 is a statement about the CURRENT code, and hand every newly surfaced
finding to t87 for disposition.

## AC draft (groom will fence these - target 5 fenced ACs, inside max_acs=6)

- **ac1 - all five reports exist, parse, and are newer than the final product
  commit.** Each JSON report parses, each .txt report carries its parsable
  summary line, and each report's timestamp/tree-hash field post-dates the
  merged t84 commit (the fence compares the recorded tree hash against
  `git rev-parse HEAD`-style measurement at verification time, expressed
  against the immutable ref the card names).
- **ac2 - gitleaks stays measured-zero and the mechanism is unchanged.** The
  refreshed gitleaks report has `[]` findings under the SAME pinned v8.30.1 +
  t36-allowlist mechanism; the `Makefile` is byte-clean (this card does not
  tune the allowlist - tuning it is a separate card with its own
  negative-control burden).
- **ac3 - the count delta is measured and reported, never suppressed.** The
  fence extracts the five counts from the refreshed reports and prints them
  against the pre-refresh values (0/32/42/3/22); any drift is listed
  finding-by-finding in the handoff as the input to t87. Suppressing a drift to
  keep a carried gate green is a FAIL - this is the t72 count-gate lesson
  inverted: the card REPORTS the new count, it does not pin the old one.
- **ac4 - carried-gate disposition for the t41 re-parse gate.** The t41 stored
  gates parse the committed reports against the committed criterion document.
  If any count drifts, the criterion document is refreshed by RUNNING ITS OWN
  GENERATOR (`backend/scripts/security_ops_verification.py`) - a machine
  regeneration, never a hand-edit - and the disposition is stated in the card:
  the generator-owned rows move, the hand-maintained criterion-13 prose is
  t89's territory and is untouched here. If the groom's measurement shows the
  generator output requires t87's register update to close the loop, the card
  says so and the loop closes at t87/t89 - an open intermediate state is
  disclosed, not hidden.
- **ac5 - delta purity.** Only the five report files differ from the named
  immutable ref (plus, IF and only if ac4's drift leg fired, the
  generator-regenerated criterion document, which the card admits explicitly as
  the sixth disclosed path); `Makefile`, `backend/`, `observability/`,
  `incident-response/`, `ops/`, `openapi.yaml`, `README.md` and every other
  `docs/` file are byte-clean.

## Constraints (hard)

- Exactly 5 files (the disclosed max_files exceedance):
  `security/gitleaks-report.json`, `security/npm-audit-report.txt`,
  `security/pip-audit-report.txt`, `security/semgrep-report.json`,
  `security/trivy-report.json`.
- The scan mechanism is FROZEN: same tools, same pinned versions, same
  allowlist construction, `Makefile` untouched. A refresh that "makes a finding
  disappear" by changing the mechanism is a FAIL, not a pass.
- No finding is dispositioned, edited away, or allowlisted by this card. The
  register/disposition loop is t87's job; this card reports what the tools
  measured.
- No CI wiring (REQ-CICD-073 forbids scan jobs in CI); the refresh is run the
  way the phase_7 refresh was run - operator-side, committed output.
- No product-code, contract, ops-doc, observability or incident-response
  change; no dependency addition (the scans READ dependencies, they do not add
  them).
- Tool availability is measured, not assumed: if a tool binary cannot run on
  this machine at build time, the card reports the leg as DEFERRED with the
  measured reason (the phase_7 deferral discipline - a deferred row is never
  written as PASS) rather than re-stamping the old report.
