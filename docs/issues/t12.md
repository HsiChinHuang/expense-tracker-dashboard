## Goal

Build the audit-writing machinery that t13/t14 integrate into their services:
the `AuditLog` model, Alembic revision `003` (table + three indexes), and
`backend/app/audit/logger.py` exposing `write_audit_log` which adds the audit
row to the CALLER's session/transaction (never commits independently), plus
the `get_client_ip` request dependency. This issue proves the atomicity
contract with a synthetic business write (real merged model + invalid audit
action): if the audit insert fails, the business write is rolled back. No
expense or budget endpoint is touched here, and no audit read endpoint is
ever created (FR-AUD-2).

Contract pins taken from the chapters (the REQs are terse; chapters are the
tie-break, all re-read during groom):

- Writer signature (Chapter 6 §6.11.1, verbatim): `write_audit_log(db,
  user_id, action, entity_type, entity_id, old_value, new_value,
  ip_address) -> None` — body is `db.add(AuditLog(...))`, **no commit, no
  independent session** ("No commit here; caller commits"). The name is
  `write_audit_log` (NOT `write_audit` as the survey draft abbreviated) —
  Chapter 12 §12.7.5's service example calls it with keyword arguments
  `db=, user_id=, action=, entity_type=, entity_id=, old_value=, new_value=,
  ip_address=`, so the parameter names are part of the contract t13/t14 call.
- `get_audit_logger` (REQ-ARCH-022): a zero-arg joinable dependency in
  `app/audit/logger.py` returning `write_audit_log` itself; no router consumes
  it in t12 (REQ-ARCH-022's DI list is satisfied by its existence + one unit
  test; expense/budget services may Depends() it in t13/t14 or call the
  function directly).
- Value-shape direction (Chapter 5 §5.7.4/§5.7.5 + Chapter 12 §12.7.2, both
  verified before pinning — not guessed): **CREATE → old_value NULL, new_value
  full; UPDATE → both populated; DELETE → old_value full, new_value NULL.**
- `get_client_ip` (Chapter 6 §6.5.4, frozen single rule, no alternatives):
  `forwarded = request.headers.get("X-Forwarded-For")` → if truthy, return
  `forwarded.split(",")[0].strip()` (FIRST hop, whitespace-stripped; an empty
  header value is falsy and falls through); else
  `request.client.host if request.client else None`. Return type
  `str | None`. No truncation logic is invented — IPv6 ≤ 45 chars fits
  `VARCHAR(45)`; the survey draft's "≤ 45 chars" clause is dropped as
  unspecified behavior.
- FK preserve rule (Chapter 6 §6.11.2 "Preserve on user delete | No cascade"):
  `audit_logs.user_id` FK is plain `ForeignKey("users.id")` with **no
  `ondelete="CASCADE"`** (unlike categories) — deleting a user with audit rows
  must fail, not silently erase history.
- Constraint/index names (Chapter 5 §5.7.2/§5.7.3/§5.8): CHECKs
  `ck_audit_action`, `ck_audit_entity_type`; indexes
  `idx_audit_user_created` (user_id, created_at DESC), `idx_audit_entity`
  (entity_type, entity_id), `idx_audit_action` (action). t13+ may reference
  these names; they are frozen.
- JSON variant (Chapter 5 §5.7.2 "Note on JSONB", REQ-DB-054):
  `JSONType = sa.JSON().with_variant(postgresql.JSONB(), "postgresql")`
  defined ONCE in `app/models/audit_log.py`, imported by revision 003
  (t10 drift-prevention precedent). All t12 tests run on SQLite (JSON stored
  as TEXT) — the AC is harness-runnable with no PostgreSQL.

## Acceptance criteria

- [ ] ac1 — `backend/app/models/audit_log.py` defines `AuditLog` (table `audit_logs`) on the shared `Base` with exactly the REQ-DB-050 columns: `id` Python-generated UUID PK (`sa.Uuid`, `default=uuid.uuid4`); `user_id` UUID **NOT NULL** FK `users.id` with **NO ondelete cascade** (audit rows are preserved on user delete — REQ-SEC-060); `action` `String(10)` NOT NULL; `entity_type` `String(20)` NOT NULL; **`entity_id` `sa.Uuid` NOT NULL with no FK (review_plan W5 frozen: on-tree REQ-DB-050 says NOT NULL; the survey's omission is dead)**; `old_value`/`new_value` nullable using `sa.JSON().with_variant(postgresql.JSONB(), "postgresql")` defined once in this module (REQ-DB-054 — a dict payload round-trips on SQLite TEXT); `ip_address` `String(45)` nullable; `created_at` `DateTime` NOT NULL `server_default=func.now()` (t6/t10 SQLite precedent, documented deviation from TIMESTAMPTZ). Named CHECKs `ck_audit_action` (`action IN ('CREATE','UPDATE','DELETE')`) and `ck_audit_entity_type` (`entity_type IN ('expense','budget')`) reject out-of-set values at INSERT; the three REQ-DB-052 indexes `idx_audit_user_created` (user_id, created_at DESC), `idx_audit_entity` (entity_type, entity_id), `idx_audit_action` (action) exist. Hand-written Alembic revision `backend/alembic/versions/003_audit_logs.py` (`revision="003"`, `down_revision="002"`, importing the JSON variant + constraint SQL from the model module per the t10 no-drift precedent) creates the table + three indexes; on a fresh SQLite file `upgrade head` yields a single head `003`, `downgrade 002` removes `audit_logs` (table and all three index names gone), and re-`upgrade head` restores it (round-trip); a dict payload written through the model round-trips as a dict on SQLite with `old_value`/`new_value` independently nullable (REQ-DB-050/051/052/054).
- [ ] ac2 — `backend/app/audit/logger.py` exposes `write_audit_log(db: Session, user_id: UUID, action: str, entity_type: str, entity_id: UUID, old_value: dict | None, new_value: dict | None, ip_address: str | None) -> None` (Chapter 6 §6.11.1 verbatim; all eight parameters usable as keyword arguments per Chapter 12 §12.7.5's call). The body only does `db.add(...)` — it never commits, never flushes-to-another-session, never opens its own session (REQ-ARCH-023/078). Pinned value shapes (REQ-DB-053, REQ-SEC-061; direction verified in Chapter 5 §5.7.4/§5.7.5 and Chapter 12 §12.7.2): CREATE → `old_value` NULL and `new_value` populated; UPDATE → both populated; DELETE → `old_value` populated and `new_value` NULL. A second-session visibility probe proves the logger never commits: after `write_audit_log` + `flush` the row is invisible to a second session and appears only after the CALLER's `commit()`; a `rollback()` instead leaves zero audit rows. `get_audit_logger()` (REQ-ARCH-022) exists in the same module, is zero-arg, and returns `write_audit_log` itself.
- [ ] ac3 — Atomicity (REQ-DB-053, REQ-PROD-021, REQ-SEC-064): one pinned failure-injection mechanism (review_plan W7) — in a single session, write a real business row (merged `Category`), call `write_audit_log(..., action="PATCH", ...)` (violating `ck_audit_action`), call the single `commit()`; the commit raises `IntegrityError`, and after `rollback()` a fresh session shows **neither the business row nor any audit row** — the business write does not survive a failed audit write. The injection must NOT fabricate an out-of-CHECK `entity_type` (only 'expense','budget' are valid) and needs no monkeypatch. t12 ac3 is the machinery proof; t13/t14 re-use this exact mechanism to prove service integration only.
