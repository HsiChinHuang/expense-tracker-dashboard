# t55 - Give the E2E suite a frontend target: dev server + /api proxy

## Context

t54 merged (97153c0) and the E2E job reached step 8 for the first time.
Measured on run 38304300231 (head_sha 142885e): steps 1-7 GREEN (browser
install now yields build 1208 matching the pinned @playwright/test 1.58.0
harness), step 8 "Run the E2E suite" EXECUTED the suite for the first time
(3 specs, real Chromium) and then failed identically in all three specs,
both attempts each:

```
Error: page.goto: net::ERR_CONNECTION_REFUSED at http://localhost:5173/register
make: *** [Makefile:101: e2e] Error 1
```

**Measured root cause (all local, daemon-free):**

- `e2e/playwright.config.ts` (REQ-TEST-040, byte-pinned by stored
  tests[136]=t27) resolves `BASE_URL = process.env.E2E_BASE_URL ??
  'http://localhost:5173'`, and every spec navigates relative URLs
  (`/register`, `/login`, `/expenses`, `/budgets`, `/`).
- `.github/workflows/e2e.yml` brings up the compose stack, waits for
  `http://localhost:8000/api/v1/health`, installs browsers, runs
  `make e2e`. **Nothing ever listens on 5173** - `docker-compose.yml`
  publishes ONLY `8000:8000` (byte-pinned PASS line
  `COMPOSE_PORT_MAPPING 8000:8000 PASS` in docs/criteria/
  infra_verification.md, asserted by stored tests[143]=t28) and no step
  starts a Vite server. ERR_CONNECTION_REFUSED is the only possible
  outcome.

**Why the obvious option (a) - point the suite at the container on :8000 -
is REJECTED by measurement, not preference:**

`backend/app/main.py` registers `@application.get("/")` (`read_root`,
returning `{"status": "ok"}`) BEFORE `register_spa_static` adds the SPA
catch-all `/{requested_path:path}`. Starlette matches routes in
registration order, so with the SPA mounted, `GET /` still returns the
JSON skeleton, NOT the SPA document. The frontend router
(`frontend/src/App.tsx`) declares `/` as the protected dashboard route,
and `happy-path.spec.ts` / `month-switch.spec.ts` do `page.goto('/')`
then assert `getByTestId('kpi-total')` - a JSON body has no test id, so
those specs would fail on content, not connection. Making option (a) work
would require reordering the backend factory (removing or demoting
`read_root`), which collides with the stored t1 smoke contract
(`backend/tests/unit/test_smoke.py`: `client.get("/")` must equal
`{"status": "ok"}`) and with tests[50]/[51]=t9. Option (a) is therefore
OUT OF SCOPE for this card by contract, and this card must NOT touch
`backend/app/main.py`.

**The chosen fix (option 2 from platform #59), two small additive edits:**

1. `frontend/vite.config.ts` gains a dev-server `/api` proxy to the
   container-served backend, so the page under test talks to the API on
   the SAME origin and no CORS is involved. This is REQUIRED, not
   optional, and the reason is measured: the backend registers NO
   `CORSMiddleware` anywhere (`grep -rn middleware backend/app` is
   empty; `CORS_ORIGINS` in `backend/app/config.py` is an unused setting
   that docker-compose merely injects). Without a proxy the browser at
   :5173 would call `:5173/api/...`, which Vite answers with the SPA
   index document (its history fallback), and every request would fail
   while the page still loads - the classic false-pass shape. The proxy
   also cannot mask a dead backend: the register flow must POST through
   it and receive a JWT for the dashboard assertions to pass.
2. `.github/workflows/e2e.yml` gains ONE step that starts the pinned Vite
   dev server in the background on 127.0.0.1:5173, inserted BETWEEN the
   health-wait step and the browser-install step. The browser install
   (npm install + Chromium download) is the natural readiness wait; the
   t26 step-ORDER contract (stored tests[133]=t26:
   `up < health < playwright install < make e2e < down`) is preserved
   because the new step sits inside the health..install gap and adds no
   `uses:` line.
