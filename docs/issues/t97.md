## Goal

Two places claim to know the app's version and they disagree: the app factory
hardcodes `0.1.0`, the settings object carries `1.0.0`, and the live health
endpoint - measured by the orchestrator - answers `"version":"0.1.0"` because it
reads the factory value. `render.yaml` and the blueprint gate both speak of
`1.0.0`. This card deletes the duplicate: one line in one file, so the deployed
payload reports the configured version and the config becomes the single source
of truth it was meant to be.

## Measured base state (factpack c_d_recon.card_D_version; DO NOT re-measure)

- Product sites:
  - `backend/app/main.py:81` is
    `application = FastAPI(title="Expense Tracker Dashboard API", version="0.1.0")`
    (survey read confirms this text at line 81 inside `create_app()`).

  - `backend/app/telemetry.py:131` already uses `settings.APP_VERSION`.
- The fix the orchestrator measured as sufficient: `main.py:81` ->
  `version=settings.APP_VERSION`, importing `settings` per the file's existing
  import style. The live health payload then reports `1.0.0` through
  `request.app.version`.
- NO stored gate in the 318-entry index pins the health body's version VALUE:
  the orchestrator scanned all entries. `openapi.yaml` pins field NAMES only and
  is FROZEN - do not touch it.
- Survey read of the backend tests confirms the shape of the risk:
  `backend/tests/integration/test_health_api.py` asserts the field set
  (`status`, `database`, `fallback_active`, `version`), that
  `body["version"]` is a `str`, and at line 69 that
  `body["version"] == application.version` - all three hold under either value,

- Live evidence at survey: `GET /api/v1/health` ->
  `200 {"status":"ok","database":"postgresql","fallback_active":false,"version":"0.1.0"}`.
